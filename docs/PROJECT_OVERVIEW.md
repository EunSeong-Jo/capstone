## 1. 프로젝트 개요

### 1.1 서비스 흐름

회원가입(또는 비회원 둘러보기) → **피부타입 진단**(6문항 QnA, 선택으로 얼굴 사진 AI 분석) → 8가지 피부타입 캐릭터 부여 →
**피부타입 맞춤 추천** + 내가 쓰는 제품을 **화장대**에 등록(검색·사진 스캔·챗봇) → 화장대 제품마다 **성분이 비슷하면서 더 싼/더 잘 맞는 대체품**과
같은 제품의 **리필·다른 용량**을 제안 → **예산 구매 가이드**(토너·에센스·크림·선크림 루틴 1~3안) → 장바구니·주문·후기·선물·AI 챗봇.

### 1.2 규모 (2026-10-29 측정)

| 항목 | 값 |
|---|---|
| 커밋 / 머지(PR 포함) | 391 / 104 (첫 커밋 2026-04-14) |
| 백엔드 Python | 약 14,000줄 (`backend/app`) · 서비스 모듈 27개 · API 라우터 14개 |
| 프론트엔드 TS/TSX | 약 26,000줄 (`frontend/src`) · 라우트 43개(+리다이렉트) |
| API 엔드포인트 | 라우터 데코레이터 72개 |
| 테스트 | 백엔드 `test_*` 함수 500개(문서 기준 pytest 573건, 파라미터 포함) · 프론트 자동 테스트 0건 |
| 제품 데이터 | 제품 4,013 · 성분 23,147 · 제품–성분 연결 163,103 · 성분 별칭 4,411 · 성분 설명 3,687 · 유사도 146,940행 · 성분 기능 라벨 1,686 · 제품×피부타입 궁합 32,104 (문서 기준) |
| 카테고리 | 얼굴용 4종: 스킨케어 · 마스크팩 · 클렌징 · 선케어 |

### 1.3 팀과 역할

조은성(팀장·프론트 통합) · 최동균(부팀장·상품 데이터·DB) · 박주원(편집·백엔드·RAG 챗봇) · 심유빈(학술·OCR·UI) · 김미송(총무·UI/UX·피부진단).
브랜치는 `기능_이니셜`(예: `swappack_es`), PR의 base는 항상 `dev`입니다.

### 1.4 사용자 페르소나 (PRD v1.8)

A 트렌드 민감형(20대 여성) · B 피부 건강 중심형(30대 직장인) · C 화장품 입문자(20대 초반). 비회원도 진단까지 가능하고(Soft-gate), 개인 데이터부터 로그인합니다.

## 2. 시스템 구조와 기술 스택

### 2.1 구성도

```
┌──────────── 사용자 ────────────┐
│  Android APK (Capacitor)  /  웹 │   ← 같은 React 번들
└──────────────┬─────────────────┘
               │  HTTPS (한 주소: 정적 파일 + /api)
┌──────────────▼─────────────────────────────────────────┐
│ AWS Lightsail 컨테이너 서비스 (ap-northeast-2)           │
│  ┌ swappy 컨테이너: FastAPI (+ 프론트 빌드 정적 서빙)   │
│  └ redis:7-alpine 컨테이너 (캐시·호출 제한 카운터)       │
└───────┬───────────────┬──────────────┬──────────────────┘
        │               │              │
   AWS Lightsail DB   외부 API        외부 API
   (PostgreSQL 16)    LLM(OpenAI→      Perfect Corp(얼굴 분석)
   ※ 개발은 Neon      Claude 체인)     CLOVA OCR · OpenWeather
```

- 운영 이미지는 `Dockerfile.prod` 한 개: Node로 프론트 빌드 → Python 3.11 슬림에 백엔드 + 빌드 결과(`/app/static`)를 얹는다. 한 주소에서 API와 화면을 같이 서빙한다.
- 얼굴 가림 검사 모델(약 16MB)은 이미지 빌드 때 미리 받는다(실패해도 빌드는 유지, 처음 쓸 때 재시도).
- 파일은 디스크에 저장하지 않는다(후기 사진·분석 이미지는 DB 테이블에 바이트로 저장).

## 4. AI·알고리즘

### 4.1 성분 유사도 엔진 (`services/similarity.py`)

전성분만 보고 두 제품이 얼마나 비슷한지 구한다(리뷰·판매량·브랜드 미사용).

```
score = ( 0.65 × 역할 가중 TF-IDF  +  0.35 × 기능 프로필 코사인  +  0.20 × 제형 일치 ) / 1.20
```
- **TF-IDF**: IDF 가중 코사인, **카테고리 안에서만** 비교하고 IDF도 카테고리별로 계산
- **역할 가중**: 활성 1.0 · 에몰리언트 0.6 · 기타 0.35 · 계면활성/점증 0.25 · 용매/방부 0.2 · 오염 이름 0 · 라벨 없음 0.6
- **기능 프로필**: 보습·진정·미백 등 기능 9종의 분포(앞 성분일수록 가중, 확신도 1 제외). 자외선차단제는 무기/유기 유형 축 추가
- **제형 일치**: 이름에서 스틱·쿠션·패드·시트·오일·폼·워터·세럼 등을 추출, 같으면 가산(모르면 중립). 리필 파우치(`리필팩/리필파우치`)는 마스크 제형으로 읽지 않는다
- **후보 정리**: 같은 제품의 용량·매수 변형은 하나로 접음(기준 제품의 변형은 프론트가 '다른 용량'으로 표시), 같은 옵션 그룹의 형제는 후보에서 제외
- **판정 보정**: `similarity_curated.csv`(AI가 0/1/2로 판정한 1,443쌍). 0점 −0.15, 2점 +0.10
- **계산 대상 제외**: `composition ≠ single`, 묶음, 성분 5개 미만 → 약 2,450건이 대상
- **응답 근거**: `sharedIngredients`(IDF 큰 순 5개), `sharedFunctions`, `method`
- **조회 API**: `GET /products/{id}/similar?method=&limit=&fitFor=` — 결과는 Redis 24시간 캐시, 유사도 없으면 빈 배열 200
- **평가 결과**: 시드 80개·판정 843건 기준 nDCG@10 **0.799**, 정밀도@5 0.468 (`scripts/eval_similarity.py`)
- 화면의 "비슷함" 초록 임계값 `SIMILARITY_HIGH`=55

### 4.2 성분 기능 분류와 피부 궁합 (`services/skin_fit.py`)

- **라벨**: 성분 1,686종(제품-성분 출현의 약 94%). 기능 9종(H B S W A O P E U) · 역할 · 플래그(I 자극, F 향, L 알코올 등) · 확신도 1~3. `ingredient_functions`는 `norm_name` 키
- **궁합 점수**
  ```
  선호 점수 = 1 − exp(−Σ 가중 / (REF[타입] × 1.9))
  감점     = Σ 기피 플래그별 (타입 가중 × 개수 보정)
  score    = 100 × (0.30 + 0.70 × 선호 점수) − 감점
  ```
- **근거 규칙**: 활성·에몰리언트 확신도 2+ 가점, 기피는 확신도 3 또는 식약처 고시 목록일 때만 근거. **하드 제외**는 고시 성분·일반 향료·건조 알코올뿐, 나머지는 감점과 "주의" 표시
- **사전 계산**: `product_skin_fit`(제품×8타입). 목록 필터·정렬·홈 추천·예산 가이드·궁합 카드·배지·전성분 칩이 모두 같은 판정을 읽는다
- **제품 성분 분석**(`services/product_analysis.py`): 기능별 강도, 주의 성분, 핵심 성분, 전성분 해부도, "내 화장대에서의 위치"

### 4.3 피부타입 진단

- 6문항 → 5축(`moisture`/`oil`/`sensitivity`/`pigmentation`/`trouble`) → 8타입 프로필과의 거리로 1~3순위. 1·2순위가 붙으면 `borderline`, 사용자가 1·2순위 중 선택(`PATCH /diagnosis/latest`)
- **8타입**: 반질반질 물개 · 얼룩덜룩 메밀묵 · 수분팡팡 옹달샘 · 바스락 사막 · 겉바속촉 수부지 · 조심조심 유리구슬 · 말랑말랑 인절미 · 울긋불긋 화산
- 채점은 프론트(`skinTypeScoring.ts`)와 서버(`services/diagnosis.py`)에 같은 로직. 문항별 가중치는 `quiz_options.weights`(DB), 8타입 프로필은 코드
- 저장: `diagnoses`(원본 답 `answers`), `diagnosis_ranks`(순위 3건), `profiles.skin_type`(최신 1순위 캐시)

### 4.4 얼굴 사진 AI 피부 분석

- **호출**: Perfect Corp 파일 등록 → 업로드 → 분석 작업 → 폴링(SD 모드). 유닛은 성공 시에만 차감
- **항목·한도**: 무료(사진 동의자) **8항목, 월 1회** / 구독 **16항목, 월 4회**. 성공한 분석만 DB 행으로 센다. 달 경계는 Asia/Seoul
- **QnA와 혼합**: 서버에서 사진 가중 0.4(`PHOTO_BLEND_WEIGHT`), 사진 전용·일부 문항+사진은 `blend_partial`(0.5). 클라이언트는 `analysisId`만 전달
- **분석 시점**: 문항 도중 촬영만 미리 하고 분석은 진단을 마칠 때 1번
- **서버 사전 검증**(`face_gate.py`, `occlusion.py`): YuNet 얼굴 검출(폭·정면·밝기·초점·잘림) + 가림 검사(볼/코·입/턱 영역별 얼굴 피부 비율) + EXIF(GPS 포함) 제거. 실패는 한도를 쓰지 않는다
- **허용 계정 + 표본**(`skin_sample.py`): 실호출은 `SKIN_ANALYSIS_ALLOWED_EMAILS`만, 그 외는 표본 계정(`SKIN_SAMPLE_EMAIL`) 분석 결과를 복사. 구독자는 표본 8항목 + 나머지 8항목은 가짜 점수·이미지
- **분석 이미지**: 업체의 마스크 PNG(얼굴 없는 투명 PNG)를 분석 직후 `skin_analysis_images`에 저장, 본인만 인증 API로 조회
- **화면**: 마이페이지 AI 피부관리(구독 상태·이용 현황·최근 분석, 연도·월일·시각 드롭다운, 항목별 막대, 분석 이미지 보기)

### 4.5 사진으로 제품 찾기 (OCR)

- 앞면 촬영(가이드 틀) → `POST /products/scan` → **CLOVA OCR**(필드를 이어 붙인 통짜 텍스트) → `pg_trgm` 제품명 대조 → **후보 목록 + "찾는 제품이 없어요"**
- 같은 제품의 단품·더블 기획·리필 기획은 `product_variants.py`가 묶고 대표는 가장 용량이 작은 제품
- 호출 한도(`ocr_quota.py`): 허용 계정 면제, 그 외 계정당 일 한도 + 전체 일 한도, Redis를 못 읽으면 차단
- 스캔 기록(`scan_results`)과 화장대 추가 경로(`added_via`)를 남긴다

### 4.6 AI 챗봇 (`api/chat.py`)

- 질문 → **RAG**(제품명·브랜드·성분명 검색, 피부타입 부적합 제품 제외) → 시스템 프롬프트에 사용자 피부타입·오늘 날씨·참고 제품 주입 → LLM
- 프롬프트 규칙: 의도 파악 → 제품 데이터에서 찾기 → 성분 기반 적합도 판단 → **제품 사실은 데이터에 있는 것만**, 성분 자체 질문은 일반 지식 허용(출처 구분 표기)
- **공급자 체인**(`llm.py`): `LLM_CHAIN=openai,claude`, 한 곳이 실패하면 다음, 전부 실패하면 `LLMUnavailable`
- **DB 폴백**(`chat_fallback.py`): 질문 유형을 키워드로 분류해 성분 설명·기능 라벨·제품 RAG·유사도·궁합을 문장 틀에 채운다(모델 없음)
- 비회원 IP당 일 한도(기본 3회, Redis)
- 챗봇으로 화장대 제품 등록 가능

### 4.7 오늘의 케어 문구와 날씨

- **케어 문구**(`GET /care-tip?skinType=`): 피부타입별 하루 1회 LLM 호출, 캐시 키에 서울 날짜. 그날 처음 생성된 문구로 고정, 프롬프트에 오늘 하루 예보(비·눈·강풍·일교차) 반영. LLM 실패 시 502 → 프론트 정적 문구
- **날씨**(`GET /weather`): OpenWeather, 서울 고정, TTL 캐시. 키가 없으면 503 → 프론트 목업 날씨

### 4.8 추천 엔진

- **홈 큐레이션**(`GET /recommendations/main`): 카탈로그 전체에서 성분 기반 점수(피부타입 매칭 + 별점 + log(리뷰 수) + 브랜드 다양성). 점수식은 `product_score.py` 한 곳에 두고 홈·예산 가이드가 공유. **성분 분석이 끝난 제품만** 추천 대상(`analysis_scope.py`)
- **피부타입 맞춤 세트**(`GET /recommendations/set`): 홈 "추천세트" — 계정의 화장대 예산을 기준으로 알뜰·균형·여유 3안
- **예산 구매 가이드**(`POST /recommendations/budget`, `budget_guide.py`): 단계(토너·에센스·크림·선크림)별 상위 20개 후보 → 합계 ≤ max인 모든 조합 완전탐색 → [min,max]를 알뜰·균형·여유 3구간으로 나눠 구간별 최고 점수 조합. 예산이 모자라면 뒤쪽 단계부터 빼며 `missing_steps`·`min_possible_total` 안내. 단계는 제품명 키워드 + 최소 용량(`routine_steps.py`)

### 4.9 교체 제안 (프론트 `useSwapSuggestion`)

- 화장대 제품(시드)마다 `/similar` 조회 → 홈 카드 3종
  - **더 저렴한 대체품**: 유사도 ≥ `HOME_SIMILARITY_MIN`(50), 절약액 순, 대체품 id 중복 제거
  - **더 좋은 대체품**: 가격 무관, 내 피부 궁합이 `FIT_GAIN_MIN`(5)점 이상 높은 것(주의 판정 제외)
  - **리필·다른 용량**: 같은 단가 단위끼리 비교해 단가가 2% 이상 싼 것
- 같은 제품의 다른 용량은 대체품에서 분리(`splitSameProductVariants`), 마스크팩(`PACK_CATEGORY`)은 시드·대체품 모두 제외
- **오늘의 시드**: 날짜 해시로 순서를 섞어 하루 5개만 조회(`MAX_SEEDS=5`), 종류가 비면 5개씩 더 물어 채움(최대 40)
- **"최대 ○○원 절약 가능"**(`useClosetMaxSaving`): 마스크팩 제외 화장대 **전체**를 id 순으로 조회해 날짜와 무관한 값. 제품마다 1등 후보 하나만 합산
- 404(카탈로그에 없는 id)는 `stale`로 안내

### 4.10 기록에서 계산하는 기능

- **알림**(`notifications.py`): 주문·포인트·후기·선물·진단 기록에서 만들고 `profiles.notifications_seen_at`만 저장
- **레벨·경험치**(`experience.py`): 스캔·후기·주문·선물 기록에서 계산(`GET /me/stats`)
- **배송 단계**(`order_stage.py`): 주문 시각에서 계산(결제완료→배송준비중→배송중→배송완료). 취소는 결제완료 단계, 반품은 배송완료 단계
- **포인트**: 구매 적립·후기 적립(+100P)·취소/반품 회수

- **계정 스코프**(`useAuth().scope`): 계정 id 또는 `guest`. localStorage 키도 계정별(`swappy:ingredients:v2:<uid>`, 최근 검색, 진단 등)
- **인증**: 액세스 토큰 30분 + 리프레시 14일(회전). 401이면 리프레시 요청 하나로 합쳐 한 번만 갱신
- **화면 규격**: 하단 탭 56px, 서브페이지 헤더 52px, 안전 영역은 `body`의 `--safe-top`, 한글은 어절 단위 줄바꿈(`word-break: keep-all` + `overflow-wrap: anywhere`)
- **목업 제품 데이터 없음**(`npm run check:dummy`로 재발 방지). 남은 목업은 제품 id가 없는 폴백(날씨·케어문구·인기 검색어 등)
- **Capacitor APK**: `frontend/scripts/android.sh debug <URL>` → `install` → `launch`. 다운로드용 `frontend/public/swappy.apk`를 서버가 `/swappy.apk`로 서빙
- **로그인 화면 데모 패널**: 로고 7번 탭으로 기기에서 켜기/끄기(`VITE_DEMO_PANEL=on`이면 기본 표시), 키 `swappy:ui:demoPanel:v2`

## 14. 고민과 결정 기록

> 1~13장은 "지금 무엇이 있는가"입니다. 이 장은 **그렇게 만든 이유**, 도중에 **고민한 대안**, **측정해 보고 버린 것**을 영역별로 모았습니다.
> 형식은 "고민 → 시도/측정 → 결정과 이유"입니다.

### 14.1 제품 방향 — 왜 "프로필 추천 → 대체품" 순서인가

- **고민**: v1.7까지는 "대체품 검색"이 메인이었다. 그러나 대체품은 "이미 쓰는 제품"이 있어야 시작되는데, 입문자(페르소나 C)는 쓰는 제품이 없다.
- **결정(v1.8)**: 진단과 프로필 추천을 입구로, 대체품 매칭은 그 다음 단계로 재배치했다.
- **Soft-gate**: 비회원도 둘러보기·진단까지 가능해야 해서(로그인 장벽을 낮춤) 채점을 프론트와 서버에 두 번 구현했다(14.5).
- **하지 않은 것**: 좋아요 브랜드 탭(브랜드 단위 찜 개념이 새로 필요해 범위 초과, 사용자 판단으로 제외), 구독 "주 1회" 강제(월 4회만 강제), 날씨 위치 개인화(위치 데이터가 없어 서울 고정).

### 14.2 데이터 — 무엇이 데이터를 오염시켰나

| 문제 | 증상 | 결정과 이유 |
|---|---|---|
| **전성분 쉼표 파싱** | 성분명에 쉼표가 있음(`1,2-헥산다이올`, `자작나무수액(10,000ppm)`). 단순 split이면 `"1"`이 5,599회로 최다 성분이 되어 유사도가 통째로 오염 | 괄호 안·숫자 사이 쉼표를 보호하는 파서 + 구분자 자동 판별. `/`는 `약모밀꽃/잎/줄기수`처럼 성분명의 일부라 구분자 아님 |
| 성분명 표기 | 판매자 표기가 제각각 | 4단계 해석, **어떤 경우에도 성분을 버리지 않음**(미매칭도 신규 등록) |
| **판매자 오타** | `포타슙`, `카퍼트라이펩사이드` | 정답지(협회 표준 21,910종)가 있으니 **LLM보다 pg_trgm 최근접 + 사람 검토**가 더 결정적 |
| **기획·묶음 상품** | `N종 택1` 기획세트는 호수별 전성분을 한 셀에 이어 붙여 "모든 성분을 가진 제품"이 되어 무엇과도 비슷 | `composition` 분류, 유사도는 single만. 고유 성분 100개 초과 비율이 단일 0.9% vs 묶음 19~29%로 20배 차이 |
| 증량·증정(`+50ml`) | 대부분 깨끗하나 39건(2.5%)은 다른 제품 성분이 이어 붙음. 이름으로 판별 불가 | 1차는 **안전한 쪽**(bonus도 제외). 성분 반복 기반 판정은 유사도 배치의 `is_bundle`에 위임 |
| **옵션형 묶음** | `[화장발]정제수…[카밍풀]정제수…` — 그대로 적재하면 255개 → 131개로 중복 소실, 제품이 모든 옵션의 합집합 | 라벨 구간별로 옵션 행 생성. **이름에 'N종'만 있는 건 나누지 않음**(세트인지 택1인지 이름으로 구별 불가) |
| 카테고리 오분류 | v5의 카테고리 154건 변경, 사유가 적힌 것은 38건 | 사람 판단이 들어간 컬럼은 **믿지 않고** 제외 목록으로 뺌. 규칙이 분명한 컬럼(전성분·상품명·용량)만 신뢰 |
| `display_name` 중복 206그룹 | 중복 행처럼 보임 | **중복이 아님**(기획/증정 구성만 다른 별도 상품, `goods_no` 다름). 의도된 정규화 |
| 단위가 다른 가격 | 10매 vs 1매 | 용량·단가 컬럼을 두고 같은 단위끼리만 비교 |
| `ewg_grade` | 크롤링으로 얻을 수 없음 | **비워 둠** — 출처 불명 숫자로 안전 등급을 주장하지 않기 위해 |
| 스킨케어 소분류 없음 | 토너·세럼·크림이 한 덩어리 | 예산 가이드는 제품명 키워드 + 단계별 최소 용량으로 분류 |
| 리뷰가 비어 있음 | 후기는 "산 제품"에만 쓸 수 있어 대부분 비어 있음 | 시연용 샘플 후기(`is_sample`)를 만들고 DB에서만 구분 |

### 14.3 유사도 — 방식 비교와 선택

**고민**: 정답 데이터가 없는데 어떤 방식이 더 좋은지 어떻게 정할 것인가.
**방법**: 시드 80개 × 후보 풀 843건을 성분 전문가 관점(AI 1명)으로 0/1/2 판정해 `similarity_gold.csv`를 만들고, 방식마다 nDCG@10·정밀도@5를 쟀다(풀 밖 후보는 0으로 세므로 방식 간 비교용).

| 방식 | nDCG@10 | 정밀도@5 | 결정 |
|---|---|---|---|
| tfidf | 0.635 | 0.330 | 유지(기준선, hybrid 미적재 시 대체) |
| hybrid v1(역할 가중 0.65 + 기능 프로필 0.35) | 0.678 | 0.343 | 이전 기본값 |
| + 변형 접기 | 0.663 | 0.338 | **채택** — 지표는 소폭↓지만 같은 제품의 다른 용량이 모두 "대체 가능"으로 판정돼 정답에 들어 있기 때문. 목적은 후보 자리를 다양하게 쓰는 것(마스크팩 1/4/5매가 상위 5칸 중 3칸을 차지하던 문제) |
| **+ 제형 일치 0.20** | **0.799** | **0.468** | **채택, 현재 기본값** |
| 제형 0.10 / 0.35 | 0.799 / 0.790 | 0.420 / 0.468 | 0.20이 최적 근처 |
| 가중 0.5/0.5, 0.8/0.2 | 0.787 / 0.777 | | 0.65/0.35 유지 |
| 자외선 유형 축 제거 | 0.797 | 0.463 | 효과는 작지만 선케어에서 +0.009라 유지 |
| 성분 임베딩 항(e5-small) | 0.800~0.801 | 0.468 | **제거** — 이득 +0.001(오차), 점수만 부풀려 임계값을 흔듦(5위 0.49→0.60), 화학명 임베딩이 약하고 기능 라벨이 이미 같은 정보 |
| jaccard / rbo | 0.603 / 0.344 | 0.273 / 0.153 | **제거** — jaccard는 IDF가 없어 흔한 성분에 끌려가고, rbo는 점수만 높고 순위 품질이 최저 |

**해석**: 가장 큰 개선은 제형 일치(0.678→0.799, 선케어 0.651→0.858, 클렌징 0.604→0.814). 스틱↔크림, 오일↔폼이 가장 흔한 0점 원인이었다.

- **왜 IDF**: 전성분 상위 6종(글리세린 85%, 정제수 84%, 1,2-헥산다이올 81%, 부틸렌글라이콜 80%, 에틸헥실글리세린 66%, 소듐하이알루로네이트 51%)이 사실상 모든 제품에 있다. 교집합이면 아무 제품이나 비슷하다. IDF가 이 성분의 가중치를 0에 가깝게 만든다.
- **왜 카테고리 안에서만**: 선케어의 대체품이 클렌징이면 안 된다. 성분만 보면 정제수·글리세린이 앞자리라 꽤 비슷하게 나온다. IDF도 카테고리별로 잡아야 같은 유기자차끼리 미세한 차이가 드러난다.
- **왜 성분 5개 미만을 뺐나**: 벡터가 짧아 흔한 성분 몇 개로 점수가 1.0 가까이 튄다.
- **판정 보정(큐레이션)**: "LLM 재순위"를 API가 아니라 **AI가 직접 판정한 CSV**로 했다. 같은 판정으로 평가하면 순환이라 지표에 넣지 않았다.
- **임계값 재설정**: `SIMILARITY_HIGH` 30→55(hybrid 분포에 맞춰 시드당 약 4개가 초록).
- **부산물**: 유사도 1.0 쌍은 같은 제품의 중복(선케어 7쌍이 전부 실제 중복) → 중복 제품 탐지 옵션.
- **공통 성분 근거에 정제수·글리세린을 보여 주지 않는 이유**: 흔한 성분을 근거로 보이면 사용자가 추천을 신뢰하지 않는다.
- **리필팩 유사도 83% 사건(최근)**: 리필 제품이 100%가 아닌 83%로 나왔다. 원인은 `리필팩`의 '팩'을 마스크 제형으로 읽어 제형 일치가 깨진 것. 리필 파우치는 제형 판별에서 제외하고, 이미 적재된 점수는 멱등 SQL(`score = old`일 때만 갱신)로 보정, 응답 캐시 키를 `form4`로 올렸다.

### 14.4 성분 기능 분류 — 규칙 기반 태그를 버린 이유

- **문제**: 기존 `ingredient_tags`는 성분 4,277종 중 10%에만 기능 태그가 있었다. 키워드로 붙인 태그라 정답 420종 대조 F1이 0.75로 부정확했다. 그래서 유사도도, "내 피부와의 궁합"도 대부분의 성분을 못 봤다.
- **결정**: AI가 성분 전문가 역할로 직접 분류(API 키 불필요 — Anthropic 키가 월 한도로 막혀 있었다). 라벨을 `norm_name` 키로 둔 이유는 id가 바뀌어도 재적재에 강하기 때문.
- **임베딩 기반 분류**: 시도 전에 보류(기능 프로필 이득이 작음).
- **분류 통일**: 목록 필터·정렬·홈·예산·카드·배지·전성분 칩이 서로 다른 말을 하지 않게 판정의 정본을 `skin_fit.py` 하나로 두고 사전 계산했다. 옛 `skin_type_rules`·`tags`는 읽지 않는다(삭제는 다음 릴리스).
- **정직하게 말하기**: 확신도 1·라벨 없는 성분은 근거로 쓰지 않는다. 하드 제외는 근거가 분명한 것만, 나머지는 감점과 "주의"로만 알린다. 진단 5축 보정은 화면에서 제거(일관성).
- **하지 못한 것**: 식약처 고시 원문 대조, CosIng 대조(접근 불가).

### 14.5 피부타입 진단

- **프론트·서버 이중 구현**: 비회원이 네트워크 없이 끝낼 수 있어야 하고(Soft-gate) 서버는 결과를 검증·보관해야 한다. "둘이 어긋나면 안 되므로 상수를 두 파일에만 둔다."
- **가중치는 DB, 프로필은 코드**: 문항이 바뀌어도 시드만 다시 돌리면 되고, 원본 응답이 남아 과거 진단을 재산정할 수 있다. 타입 정의 자체의 변경은 문항 변경과 다른 층위(과거 진단의 해석도 달라진다).
- **1·2순위 직접 선택**: 1순위와 2순위가 근소하면 사용자가 고르게 했다(`borderline`).
- **진단 전엔 개인화인 척하지 않는다**: "옹달샘을 위한 상품" 같은 문구를 쓰지 않고 "요즘 인기 있는 상품"으로 둔다.

### 14.7 사진으로 제품 찾기 — OCR과 이미지 실험

**OCR 엔진(같은 36장 + 정답 라벨)**

| 시도 | 결과 |
|---|---|
| Tesseract / EasyOCR / PaddleOCR | 범용 다국어라 한국어 성능 낮음(PaddleOCR 36.1%) |
| Surya | Windows GPU에서 vllm 미지원, llama.cpp 전환해도 모델 로딩 18분+ → 포기 |
| FSRCNN 초해상도 | cubic과 소수점까지 동일(통제 실험) → 폐기 |
| **CLOVA OCR + region-detection** | **채택** — 완전 매칭 52.8%, 완전 실패 44.4%, 이미지당 6.0초 |
| Claude Vision | API 키 무효 → 보류 |
| PaddleOCR-VL | 이미지 1장에 615초(CPU) → 탈락 |
| Upstage OCR | 가입/엔드포인트 마찰 → 포기 |

**더 파지 않은 이유**: 실패 케이스는 "화질이 낮아서"가 아니라 블러·저대비·필기체 같이 **사진에 정보가 없는** 경우였다(해상도를 올려도 결과가 같았다). 무거운 로컬 모델은 이 하드웨어에서 100배 느려진다. 그래서 OCR 엔진을 더 파는 대신 DB 매칭(Task 4.4)과 수동 검색 폴백에 시간을 썼다.

**이미지 유사도(DINOv2 vs CLIP)** — 실사진 11개 제품 22장 측정:

| 카탈로그 제품 6개를 손으로 찍은 사진 | top-1 | top-5 |
|---|---|---|
| **텍스트**(CLOVA → 제품명 대조) | **6/6** | 6/6 |
| 이미지(DINOv2-small) | 1/6 | 3/6 |

- 합성 평가 92.3%(DINOv2)·67.0%(CLIP)는 **카탈로그 이미지를 왜곡해 만든 상한**이었고 실사진에서 무너졌다. 원인: 카탈로그 이미지의 약 90%가 **판촉 배너**(깨끗한 제품컷 10%)라 손으로 찍은 병 사진과 닮을 수 없다. 모델을 바꿔도 사라지지 않는 한계.
- 둘 다 **"카탈로그에 없는 제품"을 거절하지 못한다**(점수가 겹쳐 임계값이 서지 않음) → 자동 선택하지 않고 후보 목록 + "찾는 제품이 없어요".
- 가장 치명적인 왜곡은 crop → 촬영 가이드(화면에 제품을 꽉 채우게 하는 틀)가 정확도에 직접 기여한다.
- 뒷면 사진은 정답 1위 0건 → 앞면 촬영을 안내.
- **최종**: 통짜 텍스트(브랜드 포함, 브랜드가 질의에 들어가야 오답이 1위로 오르지 않음) 매칭이 1순위. 이미지는 단독 식별이 아니라 **텍스트 후보의 재정렬에만** 쓰기로 했다(미구현).
- **한도를 fail-closed로 잡은 이유**: 챗봇은 막히는 쪽이 더 나쁘다고 보고 fail-open, OCR은 무료 호출 수가 걸린 외부 API라 Redis를 읽지 못하면 막는다. 가입을 여러 번 해도 전체 한도는 넘지 못한다.

### 14.8 챗봇

- **환각 방지**: 제품에 대한 사실(이름·가격·성분·평점)은 데이터에 있는 것만 단정. 성분 자체 질문("OO가 뭐야")은 일반 지식을 허용하되 "DB에서 검증한 정보가 아니다"를 밝힌다. 효능은 데이터에 없으므로 임상 검증을 단정하지 않는다.
- **공급자 체인과 폴백**: Anthropic 키가 월 한도로 막힌 경험에서 나왔다. 한 곳이 실패해도 다음으로 넘기고, 전부 실패하면 **모델 없이 DB로만** 답한다 — 환각이 없고 비용이 없으며 데이터에 없으면 없다고 말한다.
- **비회원 한도를 서버에서 센다**: 화면 localStorage 제한은 시크릿 창으로 우회된다.
- **RAG 이력**: 초기엔 SQLite 임시 시드(`rag_seed.py`)였으나 PostgreSQL 스키마 확정 후 `rag.py`로 교체. 피부타입 가점 스코어링은 아직 없고 평점·리뷰 수 순.
- 챗봇이 만든 제품 id(960001대)는 카탈로그 밖이라 교체 제안에서 `stale`로 처리.

### 14.9 케어 문구와 날씨

- **캐시 키에 날씨 상태를 넣었더니** 같은 날에도 날씨가 오가며 문구가 바뀌어 "탭을 오갈 때마다 재생성"처럼 보였다 → 키에서 빼고 "그날 처음 생성된 문구로 고정", 대신 오늘 하루 예보를 프롬프트에 반영.
- **날짜는 캐시 키에만** 쓰고 프롬프트에는 주지 않는다("9월 4일에는…" 같은 문구가 다음날 어색해지므로).
- **피부타입 8종 × 하루 1회**라 호출 비용·지연이 무시할 수준.
- **날씨 무효화**: 우리가 갱신을 트리거하지 않는 외부 데이터라 버전 무효화가 무의미 → TTL만.

### 14.10 추천과 예산 가이드

- **홈 추천을 프론트에서 서버로**: 원래 `useRecommendations.ts`가 제품 40개를 받아 제품명 키워드로 점수를 매겼다 — 카탈로그의 1.6%만 보고, 근거가 이름 문자열이었다. 서버가 카탈로그 전체를 성분 기반으로 고른다.
- **한 곳에 둔 점수식**: 홈 추천과 예산 가이드가 같은 `product_score.py`를 써서 "홈에서는 1등인데 가이드에는 없는" 일이 없게 했다.
- **성분 분석이 끝난 제품만 추천**: 분석 전 제품을 올리면 눌렀을 때 대체품·비교가 비어 있다. 사용자가 직접 찾는 경로(검색·스캔)에는 걸지 않는다(기획 상품만 있는 제품도 찾을 수 있어야 한다).
- **예산 가이드: 빔서치 vs 완전탐색**: 명세는 빔서치였지만 후보 20개 × 4단계면 최대 16만 조합이라 다 봐도 0.1초대다. 빔서치는 근사라 최선을 놓칠 수 있어 전수 탐색을 택했다(단계가 늘어 조합이 폭발하면 `search_combinations`만 바꾸면 된다).
- **예산이 모자랄 때**: 빈 결과 대신 뒤쪽 단계부터 빼며 살 수 있는 만큼 루틴을 낸다(바르는 순서가 우선순위).
- **단계 분류**: DB에 소분류가 없어 제품명 키워드로 나눈다(토너 191·에센스 372·크림 240·선크림 30, 세 단계에 동시에 걸리는 제품 0건).

### 14.11 교체 제안 — 데모에서 다듬은 규칙들

- **같은 제품의 대용량은 대체품이 아니다**: 분리하지 않으면 "유사도 100%" 1등이 대부분 자기 자신의 대용량이 된다. 다만 버리지 않고 "리필·다른 용량" 카드 재료로 쓴다.
- **리필은 가격이 아니라 단가**: 10매 대신 1매짜리(1,500원)를 고르면 가격은 90% 낮아 보여도 단가는 같다. 같은 단가 단위끼리 비교하고 2% 이상 싼 것만 남긴다.
- **마스크팩 제외**: 매수 차이 때문에 절약이 크게 보이기만 하고 실질 효과는 미미하다. 데모 계정의 절약 금액이 175,760원 → 37,060원 → 25,560원으로 줄며 현실적인 숫자가 됐다.
- **날마다 다른 시드 5개**: 화장대가 20개여도 홈 진입마다 20번 요청할 이유가 없다. 날짜 해시로 순서를 섞어 며칠이면 화장대 전체가 한 번씩 나오게 하고, 같은 날엔 새로고침해도 같은 제품이 나온다.
- **"최대 절약 가능"은 고정해야 한다**: 위 5개 시드의 합계를 띄우면 날마다 숫자가 바뀌었다(예: 25,560원 ↔ 6,960원). 화장대 전체를 id 순으로 조회하는 `useClosetMaxSaving`으로 분리했다.
- **합계는 제품마다 1등 하나만**: 후보를 전부 더하면 같은 제품의 대체품이 겹쳐 불가능한 금액이 나온다.
- **404는 오류가 아니다**: 화장대에는 카탈로그에 없는 id(챗봇 등록 제품 960001+, id 체계가 바뀌기 전의 localStorage)가 섞인다 → `stale`로 별도 안내.

### 14.12 "저장하지 않고 계산한다"

| 대상 | 방식 | 이유 |
|---|---|---|
| 알림 | 기록에서 만들고 `notifications_seen_at`만 저장 | 행동마다 생성 코드를 심지 않아도 되고(누락 불가), 과거 행동도 소급되고, 저장 알림과 실제 기록이 어긋날 수 없다 |
| 레벨·경험치 | 기록에서 계산 | 클라이언트 누적은 기기를 바꾸면 0부터, 콘솔에서 고쳐도 서버는 모른다 |
| 배송 단계 | 주문 시각에서 계산(간격을 짧게) | 택배 연동이 없고, 시연에서 취소(결제완료 단계)·반품(배송완료 단계)을 바로 보여 주려고 |
| 가격 인하·재입고 알림 | **만들지 않음** | 가격 이력 테이블·재입고 신청이 없어 근거 없이 흉내 내면 목업과 다름없다 |

### 14.13 프론트엔드

- **목업 제품 데이터 사건**: 예전에는 `mocks/alternatives.ts`의 가짜 제품에 붙은 id(102~109)가 실재 카탈로그 id와 겹쳐, **카드에 적힌 것과 전혀 다른 제품의 상세가 조용히 열렸다**. 목업을 걷어내고 `check:dummy`로 재발을 막았다.
- **`queryCache`를 만든 이유**: 데이터 훅이 결과를 컴포넌트 상태에만 들고 있어 하단 탭을 오가면 처음부터 다시 불렀고(로딩 자리표시자가 매번 스침), 홈은 교체 제안을 두 번(두 컴포넌트가 각자) 계산했다. 공유 요청에는 AbortSignal을 넘기지 않는다(한 화면이 내려가도 같은 결과를 기다리는 다른 화면이 있다).
- **계정별 저장소**: 로그아웃 후 게스트 화면에 이전 계정의 진단 캐릭터가 남던 버그, 다른 계정의 최근 검색이 보이던 문제를 계정 스코프 키로 해결했다.
- **한글 줄바꿈**: 브라우저 기본은 한글을 글자 단위로 끊어 "세/럼"처럼 쪼개졌다 → 어절 단위.
- **QnA 한 화면**: 폰에서 위쪽 여백(44px)과 큰 보기 카드 때문에 "다음으로" 버튼이 화면 밖으로 밀렸다. 여백·간격을 줄이고, 글자 크기를 키운 폰에서 넘치면 보기만 스크롤되고 아래 두 버튼은 고정되게 했다.
- **결과 카드 X 버튼 제거**: X와 위쪽 여백 때문에 내용이 잘렸다. 한 화면에 맞추면서 X로 닫을 때 하던 "고르지 않고 닫으면 새 진단 취소" 동작도 함께 없앴다.
- **홈 날씨 줄**: 피부타입 칩이 넓은 계정(게스트·수부지 등)에서만 날씨 글자가 어절 중간에서 꺾였다 → 줄바꿈 금지, 12px, 칩 문구 축약.
- **추천세트·챗봇 버튼**: 흰 배경이 화면과 구별되지 않아 연한 민트 + 2px 테두리 + 그림자.
- **최근 검색**: 입력 중인 글자가 전부 저장되던 문제 → Enter·blur·칩에서만 저장. `/search` 크래시("브링그린"): null 평점에 `toFixed` → `!= null` 처리.
- **로그인 화면 데모 패널 키 버전업**(`demoPanel:v2`): 이전에 켜 둔 기기가 데모 계정이 보이는 상태로 시작하던 문제.
- **화장대 담긴 경로 표시**: 매번 붙어 있으면 목록이 시끄럽다 → 마지막 방문 이후 새로 담긴 것만 한 번 보여 준다.
- **마이그레이션 revert 규칙**: PR #63/#64(`misong-qa-fix`)를 revert(#66·#67)해야 했는데 DB가 따라오지 않아 alembic이 길을 잃었다 → "DB를 먼저 downgrade → 그다음 revert".

### 14.14 보안

- **bcrypt 직접 사용**: passlib 1.7.4가 bcrypt 5.x와 맞지 않아(72바이트 초과 프로브를 새 bcrypt가 거부) 해싱 자체가 실패한다. 2020년 이후 릴리스가 없어 고쳐지길 기다릴 수 없다.
- **토큰 2개**: 액세스 토큰은 서명만 검증하므로 발급 후 취소할 수 없다 → 30분으로 짧게, 긴 수명은 리프레시가 맡고 DB 행에 `revoked_at`을 찍어 즉시 끊는다.
- **리프레시를 SHA-256으로 저장**: 256비트 난수라 무차별 대입 대상이 아니고, 매 갱신마다 조회해야 해서 느린 해시는 병목이다. 비밀번호와 달리 평문을 두지 않는 이유만 같다.
- **리프레시 회전**: 토큰이 유출돼도 정상 사용자가 한 번만 갱신하면 탈취된 쪽은 죽은 토큰을 들게 된다.
- **후기 사진 재검증**: 화면이 줄여 보내도 서버가 형식·크기를 다시 본다(수십 MB 원본이 DB에 들어가지 않게).
- **Redis 장애 시 정책이 둘로 갈린다**: 캐시·챗봇은 통과(fail-open), 돈이 걸린 한도(얼굴 분석)는 DB 카운트, OCR은 차단(fail-closed).

### 14.15 운영과 데모

- **Neon → AWS**: (1) Neon↔서버 왕복 약 200ms(서버는 서울, Neon은 오하이오)라 화면 하나에 쿼리가 여러 번이면 느림, (2) Neon 연산 한도(CU-시간)가 적재·배치로 차서 서버 DB 접속이 막힌 일이 실제로 발생(2026-10), (3) 건당 과금이 없는 고정비 구조.
- **사용자 데이터를 기준 덤프에서 뺀 이유**: 로컬 DB의 사용자 43명 중 35명이 pytest가 남긴 테스트 계정이고, 세션 토큰·주문·후기까지 섞여 있었다.
- **덤프 복원의 한계**: 데모 덤프(14.8MB)를 올릴 때 "SSL SYSCALL error: EOF"로 트랜잭션이 롤백되고 서버 쪽 잠금이 남아 로그인이 25초씩 걸렸다. 덤프를 줄이고(실제 이미지 복사 제외 9.9MB) 재시도를 넣었지만, 최종적으로는 **앱과 같은 API 경로로 채우는 시드**(`--allow-prod`)가 더 안전하다고 판단했다.
- **영구 볼륨이 없다**: 컨테이너 디스크는 재배포 때 사라지므로 후기 사진·분석 이미지는 DB 테이블에 저장한다.
- **조은성 화장대 20개 → 10개**: 절약 가능 금액이 비현실적으로 커 보였다. 리필은 마스크팩이 아니라 **액상 제품(토너·세럼)**의 리필팩으로 구성했다.
- **테스트 계정 테스터1·2**: 가입 직후 인삿말·QnA·선물 받는 쪽 화면을 보여 주려는 용도. 선물 시드의 받는 사람은 운영에 존재하는 닉네임이어야 해서 계정을 만든 뒤 시드를 고쳤다.
- **1회성 표시의 복구**: 화장대 "담긴 경로" 표시는 기기의 `closet-seen`, 알림 붉은 표시는 서버의 `notifications_seen_at`이라 둘을 따로 되돌려야 한다.
