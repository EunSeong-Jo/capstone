## 1. 한눈에 보기

### 1.1 서비스 한 줄과 핵심 흐름

회원가입(또는 비회원 둘러보기) → **피부타입 진단**(6문항 QnA, 선택으로 얼굴 사진 AI 분석) → 8가지 피부타입 캐릭터 부여 →
**피부타입 맞춤 추천** + 내가 쓰는 제품을 **화장대**에 등록(검색·사진 스캔·챗봇) → 화장대 제품마다 **성분이 비슷하면서 더 싼/더 잘 맞는 대체품**과
같은 제품의 **리필·다른 용량**을 제안 → **예산 구매 가이드**(토너·에센스·크림·선크림 루틴 1~3안) → 장바구니·주문·후기·선물·AI 챗봇.

조은성(팀장·프론트 통합) · 최동균(상품 데이터·DB) · 박주원(편집·백엔드·RAG 챗봇) · 심유빈(학술·OCR·UI) · 김미송(총무·UI/UX·피부진단).

## 2. 문제 정의와 가치 제안

PRD v1.8의 요지는 다음과 같습니다.

- **문제**: 화장품은 종류가 너무 많고, 같은 효능이어도 가격 차이가 크다. 사용자는 전성분을 읽을 수 없고, 후기·브랜드 광고에 의존한다.
- **해법**: "이름·브랜드가 아니라 **전성분**을 기준으로 비교한다."
  1. 내 피부(진단) 기준으로 어떤 제품이 맞고 안 맞는지 (궁합)
  2. 지금 쓰는 제품과 성분이 비슷한데 더 싼 제품 (대체품)
  3. 예산 안에서 루틴을 어떻게 구성할지 (구매 가이드)
- **v1.8 재정의(가치 제안 구조)**: v1.7까지는 "대체품 검색"이 메인이었으나, v1.8에서 **프로필(피부타입) 기반 추천이 입구**, 대체품 매칭은 그 다음 단계로 재배치했다.
  이유: 대체품은 "이미 쓰는 제품"이 있어야 시작되는데, 입문자(페르소나 C)는 쓰는 제품이 없다 → 진단과 추천이 먼저 있어야 한다.
- **페르소나**: A 트렌드 민감형(20대 여성) · B 피부 건강 중심형(30대 직장인) · C 화장품 입문자(20대 초반).
- **Soft-gate 정책**: 비회원도 둘러보기·진단까지 가능, 개인 데이터(화장대·주문 등)부터 로그인 요구. 그래서 진단 채점이 프론트와 서버에 **같은 로직으로 두 번** 있다(§5.3).

## 3. 시스템 구조와 기술 스택

### 3.1 구성도

```
┌──────────── 사용자 ────────────┐
│  Android APK (Capacitor)  /  웹 │   ← 같은 React 번들
└──────────────┬─────────────────┘
               │  HTTPS (한 주소: 정적 파일 + /api)
┌──────────────▼─────────────────────────────────────────┐
│ AWS Lightsail 컨테이너 서비스 (ap-northeast-2)           │
│  ┌ swappy 컨테이너: FastAPI (+ 프론트 빌드 정적 서빙)   │
│  └ redis:7-alpine 컨테이너 (캐시·호출 제한 카운터)       │
└───────┬───────────────┬──────────────┬──────────────────┘
        │               │              │
   AWS Lightsail DB   외부 API        외부 API
   (PostgreSQL 16)    LLM(OpenAI→      Perfect Corp(얼굴 분석)
   ※ 개발은 Neon      Claude 체인)     CLOVA OCR · OpenWeather
```

- 운영 이미지는 `Dockerfile.prod` 한 개: **1단계** Node로 프론트 빌드 → **2단계** Python 3.11 슬림에 백엔드 + 빌드 결과(`/app/static`)를 얹는다.
  한 주소에서 API와 화면을 같이 내므로 CORS가 필요 없고 `VITE_API_BASE_URL`은 빈 값(상대 경로)으로 고정한다.
- 얼굴 가림 검사 모델(약 16MB)은 이미지 빌드 때 미리 받고, 실패해도 빌드는 깨지 않는다(처음 쓸 때 다시 시도).
- Lightsail 컨테이너에는 **영구 볼륨이 없다** → 파일을 디스크에 저장하지 않는다(후기 사진·분석 이미지는 DB 테이블에 바이트로 저장).

### 3.2 기술 스택

| 영역 | 기술 | 비고 |
|---|---|---|
| 프론트 | React 18 · TypeScript · Vite · Tailwind CSS · framer-motion | 데이터 훅은 직접 만든 `queryCache` 사용, 외부 상태 라이브러리 없음 |
| 모바일 | **Capacitor** 디버그 APK (`frontend/android`) | 웹 번들이 APK 안에 들어 있고 API만 서버로 호출 |
| 브라우저 AI | MediaPipe (얼굴 검출) | 촬영 화면에서 얼굴 틀 안내 |
| 백엔드 | Python 3.11 · FastAPI · SQLAlchemy(async) · Alembic · structlog · Sentry | |
| DB | PostgreSQL 16 (`pg_trgm`) | 운영 AWS, 개발 Neon, 로컬 docker |
| 캐시·한도 | Redis 7 | 실패하면 DB로 폴백(캐시), 돈이 걸린 한도는 DB 카운트 |
| ML | scikit-learn식 TF-IDF/코사인(직접 구현 `services/similarity.py`) | 임베딩(e5, DINOv2, CLIP)은 실험 후 **채택 안 함** |
| OCR | 네이버 **CLOVA OCR General** | Tesseract/EasyOCR/PaddleOCR/Surya/VLM은 벤치 후 탈락 |
| 챗봇 LLM | OpenAI `gpt-4o-mini` → Anthropic Claude (체인) | 전부 실패하면 DB 기반 규칙 응답 |
| 얼굴 분석 | **Perfect Corp YouCam Skin Analysis** (SD 모드) | 유닛 비용이 있어 호출 제한·표본 대체 설계 |
| 얼굴 검증 | OpenCV YuNet(`FaceDetectorYN`) + MediaPipe selfie_multiclass(가림 검사, TFLite) | YOLO는 AGPL이라 제외 |
| 날씨 | OpenWeather (서울 고정) | |

## 4. 데이터: 수집 → 정제 → 적재

### 4.1 출처

| 데이터 | 출처 | 스크립트·위치 |
|---|---|---|
| 제품명·가격·이미지·전성분·리뷰 수·평점 | 올리브영(국내) 크롤링 → 정제본 v5 CSV (`data/raw/oliveyoung_products_v5.csv`) | `backend/app/data_collection/oliveyoung_crawler.py`, `scripts/load_products.py` |
| 성분 표준명·명칭 변경 | **대한화장품협회 성분 목록 PDF**(표준화명칭 21,910종) → 평문 CSV | `scripts/extract_ingredient_dict.py` → `data/seed/ingredient_dict.csv`, `seed_ingredients.py` |
| 영문 제품명 | 올리브영 **글로벌** 사이트 공개 JSON API | `collect_global_oliveyoung.py`, `match_kr_en.py` (전성분 TF-IDF로 한글↔영문 같은 상품 매칭 3단계) |
| 성분 설명(한 줄) | AI 작성 + 검토 → `ingredient_descriptions.csv` | `seed_ingredient_descriptions.py` |
| 성분 기능 라벨 | **AI(성분 전문가 역할)가 직접 분류** → `labels.csv` | §5.2 |
| 식약처 알레르기 유발 26종 | 저장소 `allergens_mfds.csv` | (고시 원문 대조는 아직 미수행) |

> 식약처 공공 API 수집기(`mfds_collector.py`)도 만들었지만 현재 정본 데이터는 올리브영 전성분(식약처 표준명으로 정규화)입니다.

### 4.2 적재 파이프라인 (멱등)

1. `alembic upgrade head` — 테이블 생성 + `pg_trgm`
2. `seed_ingredients.py` — 협회 표준명 + 명칭변경 + 오타 교정 CSV → `ingredients`, `ingredient_aliases`
3. `load_products.py` — 정제본 → 카테고리 교정/제외 → 필터 → dedup → **전성분 파싱** → 벌크 삽입
4. `seed_ingredient_functions.py` → `compute_skin_fit.py` — 기능 라벨과 궁합 사전 계산
5. `compute_similarities.py` — 유사도 배치(단일제품만)

모두 **멱등**(여러 번 돌려도 행수가 늘지 않음)입니다. 순서 의존을 줄이려고 예전의 보정 스크립트 둘(`apply_category_fixes`, `backfill_from_v5`)은 없앴습니다.

### 4.3 이 단계에서 부딪힌 문제와 결정

| 문제 | 증상 | 결정 |
|---|---|---|
| **전성분 쉼표 파싱** | 성분명에 쉼표가 있음(`1,2-헥산다이올`, `자작나무수액(10,000ppm)`). 단순 split이면 `"1"`이 5,599회로 **최다 성분**이 되어 유사도가 통째로 오염 | 괄호 안·숫자 사이 쉼표를 보호하는 파서(`utils/ingredients.py`), 구분자(쉼표/공백/`@`) 자동 판별, `/`는 구분자가 아님 |
| 성분명 매칭 | 판매자 표기가 제각각 | 4단계 해석: 정규화 직결 98.0% → 별칭 0.8% → 괄호 제거 후 1.2% → 그래도 못 찾으면 `code=NULL`로 **신규 등록(성분을 버리지 않음)**. 표준사전 매칭률 97.8% |
| **판매자 오타** | `포타슙`, `카퍼트라이펩사이드` 등 | LLM이 아니라 **pg_trgm 최근접(협회 21,910종)**으로 후보를 뽑고 **사람이 검토한 것만** 별칭으로 적재(`find_typo_aliases.py`) — 정답지가 있으니 문자열 유사도가 더 결정적 |
| **기획·묶음 상품** | `N종 택1` 기획세트는 호수별 전성분을 한 셀에 이어 붙임 → "모든 성분을 가진 제품"이 되어 무엇과도 비슷 | `products.composition`(single/bonus/bundle/goods/optgroup)으로 분류, **유사도는 single만**(`utils/composition.py`). 고유 성분 100개 초과 비율이 단일 0.9% vs 묶음 19~29%로 20배 차이 |
| 증량·증정(`+50ml`) | 대부분 깨끗하나 39건(2.5%)은 다른 제품 성분이 이어 붙음. 이름으로 판별 불가 | 1차는 **안전한 쪽**(bonus도 제외). 성분 반복 기반 판정은 유사도 배치의 `is_bundle`에 위임 |
| **옵션형 묶음** | `[화장발]정제수…[카밍풀]정제수…` — 라벨별 전성분이 한 칸에 | 라벨 구간별로 옵션 행을 만들고 원본은 `optgroup`으로 숨김. 화면은 그룹당 대표 1개 + 드롭다운. **이름에 'N종'만 있는 건 나누지 않음**(세트인지 택1인지 이름으로 구별 불가) |
| 카테고리 오분류 | v5의 카테고리 154건 변경, 사유가 적힌 것은 38건 | 사람 판단이 들어간 컬럼은 **믿지 않고** 제외 목록(`category_distrusted.csv`)으로 뺌. 규칙이 분명한 컬럼(전성분·상품명·용량)만 신뢰 |
| `display_name` 중복 206그룹 | 중복 행처럼 보임 | **중복이 아님** — 기획/증정 구성만 다른 별도 상품(`goods_no`가 다름). 의도된 정규화 |
| 용량·단가 | "10매 vs 1매"처럼 단위가 다름 | `volume_ml_g`, `unit_price`, 단가 라벨(ml/g/매)을 컬럼으로 두고 같은 단위끼리만 비교 |
| `ewg_grade` | 크롤링으로 얻을 수 없음 | **비워 둠** — 출처 불명 숫자로 안전 등급을 주장하지 않기 위해 |
| 스킨케어 소분류 없음 | 토너·세럼·크림이 한 덩어리 | 예산 가이드는 **제품명 키워드 + 단계별 최소 용량**으로 단계 분류(`routine_steps.py`) |

## 5. AI·알고리즘 상세

### 5.1 성분 유사도 엔진 (`services/similarity.py`, `docs/similarity.md`)

**목표**: 리뷰·판매량·브랜드를 쓰지 않고 **전성분만** 보고 두 제품이 얼마나 비슷한지 정한다.

#### (1) 왜 IDF인가
전성분 상위 6종(글리세린 85%, 정제수 84%, 1,2-헥산다이올 81%, 부틸렌글라이콜 80%, 에틸헥실글리세린 66%, 소듐하이알루로네이트 51%)이 사실상 모든 제품에 있다.
단순 교집합이면 아무 두 제품이나 비슷하다 → **IDF 가중 코사인**으로 흔한 성분의 가중치를 0에 가깝게 만들어 판테놀·마데카소사이드 같은 변별 성분이 점수를 결정하게 한다.
(회귀 방지 테스트: `test_common_ingredients_score_low`)

#### (2) 카테고리 안에서만 비교, IDF도 카테고리 안에서 계산
선케어의 대체품이 클렌징이면 안 된다. IDF를 전체 카탈로그로 잡으면 "선케어냐 아니냐"만 본다 → 카테고리별 IDF.

#### (3) 계산에서 빼는 제품
`composition ≠ single`, 묶음(성분수 비율), 성분 5개 미만(벡터가 짧아 점수가 1.0 근처로 튐) → 4,017건 중 약 2,450건이 계산 대상.

#### (4) 방식 비교와 선택 (평가 자동화)
정답 데이터가 없어 **시드 80개 × 후보 풀 843건을 성분 전문가 관점(AI)으로 0/1/2 판정**해 `data/eval/similarity_gold.csv`를 만들고 `scripts/eval_similarity.py`로 지표를 쟀다.

| 방식 | nDCG@10 | 정밀도@5 | 결정 |
|---|---|---|---|
| tfidf | 0.635 | 0.330 | 기준선·미적재 시 대체 |
| hybrid v1(역할 가중 0.65 + 기능 프로필 0.35) | 0.678 | 0.343 | |
| + 변형 접기 | 0.663 | 0.338 | **채택** (지표는 소폭↓, 후보 다양성 목적) |
| **+ 제형 일치 0.20** | **0.799** | **0.468** | **현재 기본값** |
| 제형 0.10 / 0.35 | 0.799 / 0.790 | 0.420 / 0.468 | 0.20이 최적 근처 |
| 성분 임베딩 항(e5-small) | 0.800~0.801 | 0.468 | **제거** (이득 +0.001, 점수만 부풀림) |
| jaccard / rbo | 0.603 / 0.344 | 0.273 / 0.153 | **제거** |

핵심 해석:
- **가장 큰 개선은 제형 일치**(0.678→0.799). 선케어 0.651→0.858, 클렌징 0.604→0.814. 스틱↔크림, 오일↔폼이 가장 흔한 "0점" 원인이었다.
- **임베딩은 폐기**: 화학명 임베딩이 약하고, 기능 라벨이 이미 같은 정보를 준다.
- **rbo**는 점수만 높고 순위 품질이 최저, **jaccard**는 IDF가 없어 흔한 성분에 끌려감.

#### (5) hybrid의 구성
```
score = ( 0.65 × 역할가중 TF-IDF  +  0.35 × 기능 프로필 코사인  +  0.20 × 제형 일치 ) / 1.20
```
- **역할 가중**: 활성 1.0 · 에몰리언트 0.6 · 기타 0.35 · 계면활성/점증 0.25 · 용매/방부 0.2 · 오염 이름 0 · 라벨 없음 0.6
- **기능 프로필**: 보습·진정·미백… 9종 기능의 분포(앞 성분일수록 크게, 확신도 1은 제외). 자외선차단제는 무기/유기 유형 축을 추가
- **제형 일치**: 이름에서 스틱·쿠션·패드·시트·오일·폼·워터·세럼 등을 뽑아 같으면 가산, 모르면 중립
- **같은 제품 변형 접기**: 용량·매수만 다른 제품은 하나로 접음(마스크팩 1/4/5매가 상위 5칸 중 3칸을 차지하던 문제)
- **옵션 형제 제외**: 같은 옵션 그룹의 옵션끼리는 서로의 후보가 아님
- **판정 보정(큐레이션)**: `similarity_curated.csv`(AI 성분 전문가가 직접 0/1/2 판정한 1,443쌍). 0점 −0.15, 2점 +0.10. 대상은 평가 시드 80개 + 조회가 많은 제품 60개. **같은 판정으로 평가하면 순환이라 지표에는 넣지 않았다.**
- **공통 성분 근거**: IDF 큰 순 5개(`sharedIngredients`) — 정제수·글리세린은 근거로 보여 주지 않는다(사용자가 신뢰하지 않으므로). 기능 근거는 `sharedFunctions`
- 화면의 "비슷함" 임계값(`SIMILARITY_HIGH`)은 hybrid 분포에 맞춰 30 → 55로 재설정

#### (6) 부산물과 후속 수정
- **중복 제품 탐지**: 유사도 1.0 쌍은 같은 제품이 두 번 들어간 것(선케어 7쌍 전부 실제 중복) → `--duplicates` 옵션
- **리필팩 유사도 83% 문제(최근)**: 리필 제품이 100%가 아닌 83%였다. 원인: `리필팩`의 '팩'을 마스크 제형으로 읽어 제형 일치가 깨짐 → `_REFILL_POUCH` 정규식으로 리필 파우치를 제형 판별에서 제외, SQL 보정(`scripts/fix_refill_similarity.py`, 멱등: `score = old`일 때만 갱신), 응답 캐시 키 `form4`로 올림
- **응답 캐시**: `/similar`는 Redis에 24시간 캐시(키에 버전·제형 규칙 버전 포함). 재배포하면 Redis가 비워진다.

### 5.2 성분 기능 분류(AI)와 피부 궁합 (`services/skin_fit.py`)

**문제의식**: 규칙 기반 태그(`tags`·`ingredient_tags`)는 성분 4,277종 중 **10%에만** 기능 태그가 있고, 키워드로 붙인 정답이 부정확했다(정답 420종 대조 F1 0.75). 그래서 유사도도 "내 피부와의 궁합"도 대부분의 성분을 못 봤다.

**해결**: Claude가 성분 전문가 역할로 성분을 **직접 분류**(`data/seed/ingredient_functions/labels.csv`, 현재 1,686종 · 제품-성분 출현의 약 94%).
라벨 구조: 기능 9종(H B S W A O P E U) · 역할(활성/에몰리언트/계면활성…) · 플래그(I 자극 F 향 L 알코올 등) · 확신도 1~3.
`ingredient_functions`는 id가 아니라 `norm_name`을 키로 둔다(재적재에 강함).

**궁합 판정**:
```
선호 점수 = 1 − exp(−Σ 가중 / (REF[타입] × 1.9))     # 0~1, 타입별 기준 규모로 포화
감점     = Σ 기피 플래그별 (타입 가중 × 개수 보정)
score    = 100 × (0.30 + 0.70 × 선호 점수) − 감점
```
- 활성·에몰리언트 확신도 2+ 만 가점 근거, 기피는 **확신도 3 또는 식약처 고시 목록**일 때만 근거로 사용
- 목록에서 제품을 **빼는(하드 제외)** 기준은 근거가 분명한 것만: 고시 성분·일반 향료, 건조 알코올. 나머지는 감점과 "주의" 표시로만 알림
- **정직하게 말하기**: 확신도 1·라벨 없는 성분은 근거로 쓰지 않고, 근거가 부족하면 부족하다고 표시
- 사전 계산 → `product_skin_fit`(제품×8타입). 필터·정렬·홈 추천·예산 가이드·카드·배지·전성분 칩이 **모두 같은 판정**을 읽는다(PR-1~3 "분류 통일")
- 예전 `skin_type_rules`/`tags`는 더 이상 읽지 않는다(삭제는 다음 릴리스)

**폐기·보류**: 임베딩 기반 성분 분류는 시도 전 보류(기능 프로필 이득이 작음), CosIng(유럽 성분 DB)은 접근 불가라 미수행, 알레르겐 고시 원문 대조는 미수행.

### 5.3 피부타입 진단 (QnA)

- **구조**: 6문항 → 5축 점수(`moisture`/`oil`/`sensitivity`/`pigmentation`/`trouble`) → 8타입 프로필과의 거리로 **1~3순위**.
  1·2순위가 붙으면 `borderline`으로 알리고, 사용자가 1순위/2순위 중 **직접 고른다**(`PATCH /diagnosis/latest`).
- **8타입 캐릭터**: 반질반질 물개 · 얼룩덜룩 메밀묵 · 수분팡팡 옹달샘 · 바스락 사막 · 겉바속촉 수부지 · 조심조심 유리구슬 · 말랑말랑 인절미 · 울긋불긋 화산
- **같은 채점을 두 곳에 구현**: 프론트 `skinTypeScoring.ts`(비회원이 네트워크 없이 끝낼 수 있게) + 서버 `services/diagnosis.py`(결과 검증·보관). "둘이 어긋나면 안 되므로 상수를 두 파일에만 둔다."
- **가중치는 DB**(`quiz_options.weights`): 문항이 바뀌어도 시드만 다시 돌리면 되고, `diagnoses.answers`에 원본 응답이 남아 과거 진단 재산정 가능. 반대로 **8타입 프로필은 코드에** 둔다(타입 정의 변경은 문항 변경과 다른 층위).
- **도달 가능성 검증**: 8타입이 모두 나올 수 있는지 테스트로 확인(Task 13.8).
- `diagnosis_ranks`: 순위별 결과 3건 저장. `profiles.skin_type`은 최신 1순위의 **비정규화 캐시**(원본은 `diagnosis_ranks`).

### 5.4 얼굴 사진 AI 피부 분석 (Perfect Corp)

**의도**: 캡스톤 어필 포인트로 "무료 체험 → 구독으로 매주 AI 피부관리". 얼굴 사진은 민감 정보라 **가입 시 선택 동의 + 촬영 직전 재동의** 구조.

**호출 흐름**: 파일 등록 → 서명 URL 업로드 → 분석 작업 생성 → 폴링. 유닛은 **성공했을 때만** 차감.

| 결정 | 내용 | 근거 |
|---|---|---|
| SD vs HD | **SD 기본** | 같은 사진에서 6개 중 5개가 소수점까지 동일(acne만 3.8 차이), SD가 더 싸고 해상도 조건도 느슨(짧은 변 480px) |

### 5.5 사진으로 제품 찾기 (OCR + 이미지 실험)

**실험 순서(OCR_SUMMARY.md)**: Tesseract/EasyOCR/PaddleOCR(한국어 약함) → Surya(Windows GPU 미지원, 로딩 18분+ 포기) → FSRCNN 초해상도(차이 없음) → **CLOVA OCR(채택)** → Claude Vision(키 문제) → PaddleOCR-VL(이미지 1장에 615초) → Upstage(가입 마찰).
CLOVA + region-detection: 문자 오류율 0.642, 완전 매칭 52.8%, **완전 실패 44.4%**, 이미지당 6.0초. 실패는 **블러·저대비·필기체 같이 사진에 정보가 없는 경우**(해상도를 올려도 결과가 같았음) → 엔진을 더 파지 않기로 결정.

**실제 카탈로그 매칭 실측**(`IMAGE_MATCH_SUMMARY.md`, 실사진 11개 제품 22장):

| | top-1 | top-5 |
|---|---|---|
| **텍스트**(CLOVA → pg_trgm 제품명 대조) | **6/6** | 6/6 |
| 이미지(DINOv2-small) | 1/6 | 3/6 |

- 합성 평가 92.3%(DINOv2) vs CLIP 67.0%였지만 **합성은 상한**이었고 실사진에서 무너짐. 원인: 카탈로그 이미지의 약 **90%가 판촉 배너**(깨끗한 제품컷 10%) → 손으로 찍은 병과 닮을 수 없음.
- 둘 다 **"카탈로그에 없는 제품"을 거절하지 못한다**(점수가 겹쳐 임계값이 서지 않음) → **자동 선택하지 않고 후보 목록 + "찾는 제품이 없어요"**
- **최종**: 통짜 OCR 텍스트(브랜드 포함) → 제품명 매칭이 1순위 신호. 이미지는 단독 식별이 아니라 **후보 재정렬 용도로만** 쓸 계획(미구현). 뒷면 사진은 정답 1위 0건 → 앞면 촬영 가이드 틀 제공.
- 호출 한도: 허용 계정은 면제, 그 외 계정당 일 N회 + **전체 합계 상한**(가입을 여러 번 해도 전체 한도는 못 넘김). Redis를 못 읽으면 **막는다**(fail-closed) — 챗봇과 반대로 잡은 이유: 무료 한도가 걸린 외부 호출이므로.
- 같은 제품의 단품/더블 기획/리필 기획이 후보에 나열되는 문제 → `product_variants.py`가 묶고 대표는 **가장 용량이 작은 제품**.

### 5.6 AI 챗봇 (`api/chat.py`, `services/llm.py`, `rag.py`, `chat_fallback.py`)

- **구조**: 질문 → RAG(제품명·브랜드·성분명 검색, 피부타입 부적합 제품 제외) → 시스템 프롬프트에 **사용자 피부타입·오늘 날씨·참고 제품 데이터**를 주입 → LLM
- **프롬프트 설계**: 의도 파악(제품 추천/성분 설명/비교/대체품) → 제품 데이터에서 찾기 → 피부타입 적합성은 성분 기반으로만 판단 → **제품 사실(이름·가격·성분·평점)은 데이터에 있는 것만** 말하고 추측 금지. 성분 자체 질문은 일반 지식 허용하되 "DB에서 검증한 정보가 아님"을 밝힘.
- **공급자 체인**: `LLM_CHAIN=openai,claude`. 한 곳이 실패하면(키 없음·만료·한도·타임아웃) 다음 공급자. Ollama 로컬 옵션.
- **폴백(`chat_fallback.py`)**: 전부 실패하면 **모델 없이 DB로만** 답한다 — 질문 유형을 키워드로 가르고 성분 설명·기능 라벨·제품 RAG·유사도·피부 궁합을 문장 틀에 채움. **환각이 없고 비용이 없으며 데이터에 없으면 없다고 말한다.** (Anthropic 키가 월 한도로 막혔던 경험에서 나온 설계)
- **비회원 호출 제한**: IP당 하루 N회(Redis, `GUEST_CHAT_DAILY_LIMIT=3`). 화면 localStorage 제한은 시크릿 창으로 우회되므로 **서버가 센다**. Redis 장애 시 통과(fail-open) — 챗봇은 막히는 쪽이 더 나쁘다고 판단.
- **RAG 이력**: 초기엔 SQLite 임시 시드(`rag_seed.py`)였으나 PostgreSQL 스키마 확정 후 `rag.py`로 교체.
- 챗봇으로 화장대 제품 등록도 가능(챗봇이 만든 제품 id는 960001대로 카탈로그 밖 → 교체 제안에서 `stale` 처리).

### 5.7 오늘의 케어 문구와 날씨

- **케어 문구(`/care-tip`)**: 피부타입별로 **하루 1번만** LLM 호출(캐시 키에 서울 날짜). 피부타입 8종뿐이라 트래픽이 많아도 비용·지연 무시 가능.
  - **그날 처음 생성된 문구로 고정**: 처음엔 키에 날씨 상태까지 넣었더니 날씨가 오가며 같은 날 문구가 바뀌어 "탭을 오갈 때마다 재생성"처럼 보임 → 날씨 상태를 키에서 제거하고, 대신 **오늘 하루 예보(비·눈·강풍·일교차)**를 프롬프트에 반영.
  - 날짜는 캐시 키에만 쓰고 프롬프트에는 주지 않는다("9월 4일에는…" 같은 문구가 다음날 어색해지므로). LLM이 막히면 502 → 프론트가 정적 문구.
- **날씨(`/weather`)**: OpenWeather, **서울 고정**(위치 데이터가 없어 개인화 불가). TTL 캐시(날씨는 우리가 갱신을 트리거하지 않는 외부 데이터라 버전 무효화가 무의미). 키 없으면 503 → 프론트가 목업 날씨.

### 5.8 추천 엔진

**홈 큐레이션 (`/recommendations/main`)** — 원래 프론트가 제품 40개를 받아 제품명 키워드로 점수를 매겼다(카탈로그의 1.6%만 보고, 근거가 이름 문자열). 서버로 옮겨 **카탈로그 전체**에서 **성분 기반**으로 고른다.
`product_score.py` 점수: 피부타입 매칭 + 별점 + log(리뷰 수) (+ 브랜드 다양성 후처리). 홈과 예산 가이드가 **같은 점수식**을 써서 "홈 1등인데 가이드엔 없는" 일이 없게 한 곳에 둔다.
**추천 대상은 "성분 분석이 끝난 제품"만**(`analysis_scope.py`) — 분석 전 제품을 올리면 눌렀을 때 대체품·비교가 비어 있기 때문. 반대로 사용자가 직접 찾는 경로(검색·스캔)에는 걸지 않는다.

**피부타입 맞춤 세트 (`/recommendations/set`, 홈 "추천세트")** — 토너·에센스·크림·선크림 루틴을 짜 준다. 세트의 예산은 계정의 화장대 예산을 그대로 쓴다.

**예산 구매 가이드 (`services/budget_guide.py`, `POST /recommendations/budget`)**:
1. 단계(토너·에센스·크림·선크림)마다 상위 20개 후보(홈과 같은 점수, 피부타입 기피 성분·무향/무알코올 선호 제품 제외, 화장대에 이미 있는 제품 제외)
2. **완전탐색**: 합계가 max를 넘지 않는 모든 조합(최대 20⁴=16만, 0.1초대). 명세는 빔서치였지만 근사라 최선을 놓칠 수 있어 전수 탐색 선택(`search_combinations`만 바꾸면 교체 가능)
3. [min, max]를 **알뜰·균형·여유** 3구간으로 나눠 구간마다 최고 점수 조합 → 1~3안
4. 예산이 부족하면 빈 결과가 아니라 **뒤쪽 단계부터 빼며** 살 수 있는 만큼(`missing_steps`, `min_possible_total` 안내)
- 엔진·탐색은 DB를 모르는 **순수 함수**라 단위 테스트

### 5.9 교체 제안 로직 (프론트 `useSwapSuggestion`) — 최근 가장 많이 다듬은 부분

화장대 제품(시드)마다 `/similar`를 물어 후보를 만든 뒤 홈 카드 3종을 채운다.
- **더 저렴한 대체품**: 유사도 하한 `HOME_SIMILARITY_MIN=50`, 절약액 순. 같은 대체품이 여러 시드에서 중복되면 id로 한 번만
- **더 좋은 대체품**: 가격 무관, 내 피부 궁합이 `FIT_GAIN_MIN=5`점 이상 높은 것(주의 판정 제외)
- **리필·다른 용량**: "값이 싸다"가 아니라 **단가가 싸다**. 10매짜리 대신 1매짜리(1,500원)는 가격이 90% 낮아도 단가는 같으므로 절약이 아님 → 같은 단가 단위끼리 비교하고 2% 이상 더 싼 것만
- **같은 제품의 다른 용량은 교체 제안이 아님**(그렇지 않으면 유사도 100% 1등이 자기 자신의 대용량이 된다) → `splitSameProductVariants`로 분리하되 버리지 않고 리필 카드 재료로 사용
- **마스크팩 제외(최근)**: 매수 차이로 절약이 커 보이기만 하고 실제 절약은 미미 → 쓰던 제품·대체품 모두 마스크팩은 교체 제안에서 제외(화장대·검색·"내 마스크팩 제품과 비슷한 추천"에는 그대로)
- **날마다 다른 5개 시드**(`orderSeedsOfToday`): 화장대가 20개여도 홈 진입마다 20번 요청하지 않도록 날짜 해시로 순서를 섞어 앞 5개만 조회. 3종 카드 중 비는 종류가 있으면 5개씩 더 물어 채움(최대 40개). 같은 날엔 같은 제품(새로고침해도 안 바뀜), 며칠이면 화장대 전체가 한 번씩 나온다.
- **상단 "최대 ○○원 절약 가능"(최근 변경)**: 위 5개 시드의 합계로 띄우면 숫자가 날마다 바뀜 → `useClosetMaxSaving`이 마스크팩 제외 화장대 **전체를 id 순으로** 물어 날짜와 무관한 최대값을 낸다. 합계 규칙은 같다(제품마다 1등 후보 하나만 더함 — 후보를 전부 더하면 같은 제품의 대체품이 겹쳐 불가능한 금액이 나옴).
- 404(카탈로그에 없는 id)는 오류가 아니라 `stale`로 처리해 별도 안내(챗봇 등록 제품·옛 localStorage)

### 5.10 "저장하지 않고 계산한다" — 반복해서 쓴 설계 원칙

| 대상 | 방식 | 이유 |
|---|---|---|
| **알림**(`notifications.py`) | 알림 행을 저장하지 않고 주문·포인트·후기·선물·진단 **기록에서 뽑아 만든다**. 저장은 `notifications_seen_at`(어디까지 읽었는지) 하나 | 행동마다 알림 생성 코드를 심지 않아도 되고(누락 불가), 과거 행동도 소급되고, 저장 알림과 실제 기록이 어긋날 수 없다 |
| **레벨·경험치**(`experience.py`) | 스캔·후기·주문·선물 **기록에서 계산** | 클라이언트 누적 방식은 기기를 바꾸면 0부터. 서버에서 계산하면 소급·정합 |
| **배송 단계**(`order_stage.py`) | 저장 없이 **주문 시각에서 계산**(결제완료→배송준비→배송중→배송완료, 간격을 짧게) | 택배 연동이 없고, 시연에서 취소(결제완료 단계)·반품(배송완료 단계)을 바로 보여 주려고 |
| 가격 인하·재입고 알림 | **만들지 않음** | 가격 이력 테이블·재입고 신청이 없어 근거 없이 흉내 내면 목업과 같다 |

## 6. 기능 카탈로그 (화면별)

라우트 기준(`frontend/src/App.tsx`). `mine()`으로 감싼 화면은 로그인 필요(`RequireAuth`가 게스트를 로그인으로 보냄).

### 시작·계정
- **스플래시** `/` — 마스코트 애니메이션 후 로그인으로
- **로그인** `/login` — 이메일 로그인, **로그인 없이 둘러보기**(게스트), 가입, 비밀번호 찾기(현재 "준비 중" + 고객센터 안내). 로고 7번 연타로 **데모 계정 패널**(기기 단위 on/off, 기본 숨김)
- **회원가입** `/signup` — 닉네임·이메일·비밀번호(8자+)·얼굴 사진 수집 선택 동의
- **온보딩/진단** `/onboarding` — 인삿말 3장 → "피부타입 알아요/몰라요" → (알면) 8종 직접 선택 / (모르면) QnA 6문항 → AI 얼굴 분석 안내(선택) → 분석 중 → 결과 메시지 → **결과 카드**(1·2순위 중 선택) → 맞춤 추천 받기. 진단 기록이 있으면 홈으로 보냄. `/qna`는 재진단 진입
- **결과 카드**: X 버튼 없이 한 화면에 들어오게 맞춤(최근 변경)

### 홈 `/home`
- 상단 앱바: 알림(미읽음 배지)·검색·장바구니(수량 배지)
- **프로필 대시보드**: 날씨·온도·습도 + 피부타입 칩, 캐릭터(탭하면 꾸미기), **오늘의 케어 문구**(말풍선), 레벨·경험치, "최대 ○○원 절약 가능"
- **오늘의 교체 제안**(슬라이드 3종: 더 저렴한 / 더 좋은 / 리필·다른 용량) + 전체 보기(`/home/cheaper-alternatives`)
- **피부타입을 위한 상품**(진단 전엔 "요즘 인기 있는 상품" — 개인화인 척하지 않음)
- **내 ○○ 제품과 비슷한 추천**: 화장대 카테고리별 구역(스킨케어·선케어·마스크팩·클렌징)
- 플로팅 **추천세트** · **챗봇** 버튼(민트 배경 + 테두리 + 그림자)

### 탐색·상품
- **카테고리** `/category`, `/category/:slug` — 정렬(인기·평점·가격 오름/내림), 피부타입 필터
- **검색** `/search` — 통합검색(제품명)·성분검색(성분 사전 기능별 탐색, **마이 성분** 저장 ♥), 인기 검색어, 최근 검색(계정별, Enter/blur/칩에서만 저장), 카메라 아이콘으로 스캔
- **제품 상세** `/detail/:id` — 이미지·가격·후기·평점, **내 피부와의 궁합 카드**, 전성분(칩·성분 설명 시트), 성분 비교 진입, 선물·장바구니·바로 구매, 옵션 드롭다운
- **성분 분석** `/analysis/:id` — 내 피부 상태와 견주면(좋은 점/아쉬운 점/신경 쓸 필요), 이 제품이 하는 일(기능별 막대), 주의 성분, 전성분 해부도, **내 화장대에서의 위치**
- **대체품 찾기** `/alternatives` — 시드 전환, 유사도순/가격 낮은순/내 피부 궁합 정렬, 공통 성분·기능 근거, 리필·다른 용량
- **성분 비교** `/compare?a=&b=` — 내 제품 vs 대체품(가격·기능 강도·내 피부 궁합·주의 성분)

### 화장대·기록
- **내 화장대** `/closet` — 보유 중/삭제된 제품, 카테고리 필터, 예산 슬라이더(0~20만원+), 담긴 경로 표시("검색으로 추가" 등, **마지막 방문 이후 새로 담긴 것만** 한 번 보여 줌), 사용 안내(닫으면 다시 안 뜸), 무료 한도 20개

## 9. 프론트엔드 설계

### 9.1 구조 원칙
- **`src/api/`** 호출 래퍼 · **`hooks/`** 데이터 훅 28개 · **`context/`** 전역 상태(Auth·Cart·Closet·Diagnosis·Liked·UserProfile·Character·Toast) · **`pages/`** 라우트 단위 · **`components/`** 기능별
- **목업 제품 데이터 금지**(`npm run check:dummy`): 예전엔 `mocks/alternatives.ts`의 가짜 제품 id(102~109)가 실재 카탈로그 id와 겹쳐 **카드에 적힌 것과 전혀 다른 제품 상세가 조용히 열렸다**. 전 화면이 실 API만 본다. 남은 목업은 제품 id를 안 담는 것(날씨·케어문구 오프라인 폴백, 인기 검색어 등)뿐
- **화면 규격 표준**(2026-07 UI 통일): 하단 탭 56px, 서브페이지 헤더 52px, 안전 영역은 `body`의 `--safe-top`이 담당(화면별로 중복 적용하지 않음)
- **한글은 어절 단위 줄바꿈**(`word-break: keep-all` + `overflow-wrap: anywhere`) — 기본값이 글자 단위라 "세/럼"처럼 쪼개짐

### 9.2 상태·캐시
- **`queryCache`**(자체 구현): 탭 이동 때 로딩 깜빡임과 중복 계산 제거. `peek`(렌더 중 동기 읽기) · `load`(신선하면 캐시, **같은 키의 진행 중 요청 공유**) · `put`/`invalidate`. 개인 데이터 키는 `me:{scope}:…`로 시작해 **세션 종료 시 통째로 삭제**(다음 계정이 보면 안 됨). 공유 요청에는 AbortSignal을 넘기지 않음
- **계정 스코프(`useAuth().scope`)**: 계정 id 또는 `guest`. localStorage 키도 계정별(`swappy:ingredients:v2:<uid>`, 최근 검색, 진단 등) → 같은 기기에서 계정이 바뀌어도 섞이지 않음. (로그아웃 후 게스트에 이전 계정의 진단 캐릭터가 남던 버그를 이 구조로 수정)
- 인증 토큰: 액세스 30분(메모리/저장소) + 리프레시 14일(**회전**, 서버엔 해시만 저장). 401이면 **리프레시 요청은 하나로 합쳐** 한 번만 갱신

### 9.3 모바일 앱 (Capacitor)
- `frontend/scripts/android.sh debug <URL>` → `install` → `launch`. 웹 번들을 APK에 넣고 `dist/swappy.apk`는 `cap sync` 전에 제거(재귀 포함 방지). 안드로이드는 엣지-투-엣지라 시스템 바 높이를 `--safe-area-inset-*`로 주입받는다
- 다운로드용 `frontend/public/swappy.apk`를 저장소에 두고, 서버가 `/swappy.apk`로 서빙(바이트 수로 배포 확인)
- 앱 위에 **로그인 화면 데모 패널**(로고 7번 탭): `VITE_DEMO_PANEL=on`이거나 기기에서 켜기. 키 버전(`demoPanel:v2`)을 올려 이전에 켜 둔 기기의 상태를 초기화

### 9.4 최근 UI·UX 개선 (QA에서 나온 것들)
- QnA 화면: 폰에서 "다음으로" 버튼이 화면 밖으로 밀리던 문제 → 한 화면에 맞추고 하단 버튼 고정, 넘치면 문항만 스크롤
- 홈 날씨 줄: 피부타입 칩이 넓은 계정에서 날씨 글자가 꺾이던 문제 → 줄바꿈 금지 + 12px + 칩 문구 축약
- 홈 섹션 제목 18px 통일, "비슷한 추천" 제목 이모지 제거·한 줄 유지
- 추천세트·챗봇 플로팅 버튼: 흰 배경이 화면과 구별 안 됨 → 연한 민트 + 2px 테두리 + 그림자
- 화장대: 카테고리 칩 필터(20개까지 늘어난 목록 대응), 무료 한도 안(10개 안팎)으로 데모 구성
- null 평점으로 `toFixed` 크래시 → `!= null` 처리, 최근 검색은 입력 중이 아니라 **확정 시점에만** 저장

## 10. 보안·개인정보·비용·한도

| 영역 | 설계 |
|---|---|
| 비밀번호 | **bcrypt를 직접 사용**(passlib 1.7.4가 bcrypt 5.x와 맞지 않아 해싱 자체가 실패 → 2020년 이후 릴리스 없는 라이브러리를 기다리지 않음) |
| 토큰 | 액세스 30분(서명 검증만이라 취소 불가 → 짧게) / 리프레시는 DB 행 + `revoked_at`. **리프레시는 SHA-256 해시로 저장**(256비트 난수라 무차별 대입 대상이 아니고 매 갱신 조회라 느린 해시는 병목). 갱신마다 **회전**(탈취된 쪽은 죽은 토큰을 들게 됨). 비밀번호 변경 시 다른 세션 모두 폐기 |
| 선택 인증 | `get_optional_user` — 같은 엔드포인트가 비회원도 허용하고 로그인 상태면 개인화 |
| 얼굴 사진 | 가입 시 선택 동의 + 촬영 직전 재동의, 원본은 메모리에서만(EXIF·GPS 제거), 얼굴 아닌 사진은 외부 전송 전 차단, 분석 이미지는 얼굴 없는 PNG만 본인만 접근, 동의 철회 가능. **동의·개인정보 문구는 데모용이라 법무 검토 필요** |
| 후기 사진 | 화면이 줄여 보내도 서버가 형식·크기를 다시 검증(수십 MB 원본이 DB에 들어가지 않게) |
| 외부 호출 비용 | 챗봇(비회원 IP 일 한도, fail-open) · OCR(계정/전체 일 한도, **fail-closed**) · 얼굴 분석(월 한도는 DB 카운트, 허용 계정 외 표본 대체) · 케어 문구(하루 8회 상한) |
| 캐시 장애 | Redis가 죽어도 500 금지 — 캐시 헬퍼는 예외를 삼키고 DB로 폴백. 단 **돈이 걸린 한도는 Redis에 두지 않는다** |
| 크롤링·API 약관 | PRD §15에서 검토(공공 API 이용 규정, 크롤링 범위) |
| `.env` | 커밋 금지, **`source .env` 금지**(통째로 읽으면 DB 비밀번호가 출력됨 — 필요한 줄만 grep) |
| 운영 DB 쓰기 | 덤프 복원은 연결이 끊길 수 있어(14.8MB 덤프에서 SSL EOF) **API 경유 시드**(`seed_demo_account.py --allow-prod`)를 사용, 운영 URL에는 플래그가 있어야만 쓴다 |

## 12. 배포·운영·데모

### 12.1 환경 3종
| | 용도 | 접속 |
|---|---|---|
| Neon(미국 오하이오) | 개발·테스트(팀 공용) | 루트 `.env`의 `DATABASE_DSN` |
| **AWS Lightsail DB(서울)** | **운영** | `.env.aws`의 `AWS_DATABASE_DSN` (커밋 금지) |
| 로컬 Postgres(docker) | 내 PC 개발·pytest | docker compose |

**AWS로 옮긴 이유**: (1) 속도 — Neon↔서버 왕복 약 200ms라 화면 하나에 쿼리가 여러 번이면 느림, (2) 한도 — Neon CU-시간 한도가 적재·배치로 차서 서버 DB 접속이 막힌 일이 실제 발생(2026-10), (3) 비용 구조 — 건당 과금이 아닌 고정비.
`scripts/aws_db.sh`가 덤프(로컬 → `~/swappy-dumps/`)·복원·SQL 실행(`sql 파일 --yes`)을 담당. 사용자 데이터는 기준 덤프에서 빼고(테스트 계정 35개 등) 데모 계정만 따로 올림.

### 12.2 배포 절차 (Lightsail 컨테이너 서비스 `swappy`)
1. `docker build --network=host -f Dockerfile.prod -t swappy:latest .`
2. `aws lightsail push-container-image --service-name swappy --label web --image swappy:latest` → `:swappy.web.N`
3. 콘솔에서 이미지 교체(컨테이너 `swappy` + `redis:7-alpine`)
4. 읽기 전용 확인: 상태 `RUNNING`, `/health`, 주요 API, `/swappy.apk` 바이트 수
- 재배포하면 Redis가 비워져 `/similar` 24h 캐시가 초기화됨(첫 조회 지연)
- 이미지에 **다운로드용 APK**가 함께 들어가므로, APK를 먼저 갱신(PR)한 뒤 이미지를 빌드한다
- 운영 배포 이력: web.1 → … → **web.15**(2026-10-29)

### 12.3 시연(데모) 설계

## 14. 알려진 한계와 다음 과제

**데이터·알고리즘**
- 이미지 재정렬(re-rank) 미구현, 실기기 OCR 인식률 측정 미완. 사진 점수-진단 혼합 계수는 사진 1장 기준
- 성분 기능 라벨은 사용 빈도 꼬리 약 2,700종이 미분류(출현 빈도 1~2회)
- 식약처 고시 원문 대조·CosIng 대조 미수행
- 스킨케어 소분류 없음(키워드로 단계 분류), 선케어 계산 대상 제품이 적어(60건) 대체품 품질이 가장 먼저 나빠지는 자리
- 날씨·케어 문구는 서울 기준

**제품·운영**
- 비밀번호 찾기 미구현(고객센터 안내), OAuth(카카오·구글) 미구현(Task 12.6), 구독 결제 없음(데모), 택배사 연동 없음(배송 단계는 시간 계산)
- 받은 선물 수락·실제 결제 연결 없음("기록만")
- 메인 화면 문구 3개 제거, 더 연한 초록 계열 색상 조정, "타입 미리 정하기" 버튼, 마이페이지 상단 고정 등 이슈 #8 항목 일부 미반영
- 챗봇: LLM 실제 응답은 키 상태에 의존(막히면 DB 폴백). `OPENAI_API_KEY`·DB public 모드·IAM 키·옛 스냅샷 정리 등 **운영 정리 항목** 남음
- 프론트 자동 테스트 없음

| 용어 | 뜻 |
|---|---|
| 화장대(closet) | 사용자가 쓰는 제품 목록(무료 20개). 교체 제안·비슷한 추천의 기준 |
| 시드(seed) | 유사도·교체 제안에서 "기준이 되는 제품"(쓰던 제품) |
| 궁합(skin fit) | 제품 전성분과 내 피부타입의 적합도(0~100, 주의 판정 포함) |
| hybrid | 역할 가중 TF-IDF + 기능 프로필 + 제형 일치로 만든 유사도 방식 |
| composition | 제품 구성 구분: single / bonus / bundle / goods / optgroup |
| Soft-gate | 비회원도 진단까지, 개인 데이터부터 로그인 |
| scope | 프론트의 계정 구분 키(계정 id 또는 `guest`) |
| 허용 계정 / 표본 계정 | 얼굴 분석을 실제로 호출할 수 있는 계정 / 대신 결과를 빌려 주는 계정(`eunseong@swappy.app`) |
| `:swappy.web.N` | Lightsail에 푸시한 이미지 태그(현재 web.15) |
