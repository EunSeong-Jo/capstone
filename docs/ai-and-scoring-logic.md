## 3. 피부타입 진단 (QnA)

**파일**: `services/diagnosis.py` (프론트 `src/data/skinTypeScoring.ts`와 동일 로직을 의도적으로 이중 구현 — 비회원 오프라인 진단 때문)

### 3-1. 5축 점수
- 축: `moisture`(수분) · `oil`(유분) · `sensitivity`(민감) · `pigmentation`(색소) · `trouble`(트러블)
- 모든 축은 **5에서 시작**, 문항 선택지마다 축별 증감(`quiz_options.weights`, DB)을 더한 뒤 **0~10으로 자름**
- 미응답 문항은 아무것도 더하지 않음 → 중간에 그만두면 '보통'에 가까워짐
- 모르는 문항·선택지는 무시(문항 개정 후 옛 응답이 와도 진단이 깨지지 않게)

### 3-1b. 문항별 선택지 가중치 (`frontend/src/data/skinTypeScoring.ts`의 `DELTAS`)

이 값이 원본이고, `scripts/seed_quiz.py`가 정규식으로 파싱해 DB `quiz_options.weights`로 옮깁니다(원본이 프론트인 이유: 비회원도 네트워크 없이 진단을 끝내야 해서). 문항은 6개, 선택지는 문항당 4개입니다.

| 문항 | 선택지 순서별 축 증감 |
|---|---|
| Q1 아침 물세수 1시간 후 | ①전체 당김 수분−3·유분−2 / ②T존 번들·볼 당김 수분−2·유분+2 / ③전체 기름 유분+3 / ④당김도 기름도 없음 수분+2 |
| Q2 자극 반응 | ①쉽게 붉어짐 민감+3 / ②컨디션 나쁘면 뾰루지 민감+2·트러블+1 / ③환절기만 각질 민감+1·수분−1 / ④늘 평온 민감−2 |
| Q3 여드름·홍조 빈도 | ①365일 트러블+3·민감+1 / ②유분 많아 좁쌀 트러블+2·유분+2 / ③생리 전 등 트러블+1 / ④거의 없음 트러블−2 |

| Q5 메이크업 무너짐 | ①전체 번들 유분+3 / ②겉번들 속당김 유분+2·수분−2 / ③코 주변만 유분+1 / ④유분 덕에 유지 유분+2·수분+1 |

- 결과적으로 **색소 축은 Q4①(+3)과 Q6④(+1)만**, **트러블 축은 Q2·Q3·Q4**에서만 움직입니다. 메밀묵(색소 9)은 5+3+1=9가 되어 두 문항을 모두 특정 선택지로 답해야만 도달합니다.

### 3-3. 순위 산출 (`rank_types`)
1. 내 5축과 각 타입 프로필의 **유클리드 거리 d**
2. 근사도 `1 / (1 + d)`
3. 상위 **3개**만 합이 1이 되게 정규화 → 화면의 "92%" 같은 값
   (8개 전체로 나누면 1순위도 20%대로 낮아 보여서 상위 3개로 한정)
4. **경계 타입**: 1·2순위 점수 차 ≤ **0.03** 이면 `borderline: true` ("OO에 가깝지만 XX 성향도 있어요")

## 4. 얼굴 사진 AI 분석

### 4-1. 파이프라인

```
앱(MediaPipe 얼굴 확인)
  → 서버 사전 검증 (YuNet 얼굴 검출 → 규칙 판정 → MediaPipe 가림 검사)
  → EXIF(GPS 포함) 제거한 JPEG 재생성, 긴 변 2560px로 축소
  → Perfect Corp: 파일 등록 → 업로드 → 작업 생성 → 폴링(최대 60초)
  → 항목별 raw/ui 점수 + 피부 분류 + 분석 이미지(mask)
  → 진단 5축으로 변환 → (QnA와 혼합) → 8타입 순위
```

### 4-2. 사전 검증 임계값 (`config.py`, 모두 튜닝 대상)

| 항목 | 값 | 의미 |
|---|---|---|
| `FACE_MIN_SCORE` | 0.8 | 검출 신뢰도 |
| `FACE_MIN_WIDTH_RATIO` | 0.60 | 얼굴 폭 / 사진 폭 (업체 요구 60%) |
| `FACE_MIN_BOX_RATIO` | 0.40 | 눈 위치를 못 얻을 때의 대체 기준 |
| `FACE_MAX_ROLL_DEG` | 15° | 기울기 |
| `FACE_MAX_YAW_OFFSET` | 0.12 | 정면 여부 |
| `FACE_MIN/MAX_LUMINANCE` | 50 / 200 | 밝기 |
| `FACE_MAX_LIGHT_IMBALANCE` | 0.4 | 좌우 조명 불균형 |
| `FACE_MIN_SHARPNESS` | 60 | 초점 |
| `FACE_SKIN_MIN_CHEEK / NOSE_MOUTH / CHIN` | 0.70 / 0.80 / 0.60 | 영역별 **얼굴 피부 픽셀 비율** (손·마스크 가림 감지) |

- 가림 기준은 업체가 정상 처리한 시험 사진(볼 95%·코입 100%·턱 76~79%)과 마스크/손을 그려 넣은 합성 사진(코입 25~49%·턱 6~48%)으로 잡음 → **실제 손·마스크 사진으로는 아직 조정 안 됨**(코드 주석에 명시)
- 애매하면 통과, 가림 모델을 못 읽으면 그 검사만 건너뜀
- 실패는 **한도를 쓰지 않음**

### 4-3. 분석 항목 · 이용 한도 (`services/skin_quota.py`)

| | 무료(동의) | 구독 |
|---|---|---|
| 월 횟수 | `SKIN_FREE_MONTHLY = 1` | `SKIN_SUBSCRIBER_MONTHLY = 4` |
| 항목 수 | 8 (oiliness·moisture·redness·age_spot·acne·skin_type·pore·wrinkle) | 16 (+firmness·radiance·texture·dark_circle·eye_bag·눈꺼풀 2·tear_trough) |
| 업체 유닛 | 5~8개 구간 12유닛 | 13~16개 구간 16유닛 |

- 동의하지 않으면 0회, 달 경계는 Asia/Seoul 1일 0시, **성공한 분석만** 센다(DB `skin_analyses` 행 수로 계산 — Redis 장애에 한도가 풀리지 않게)
- `SKIN_ANALYSIS_ALLOWED_EMAILS`에 있는 계정만 실제 업체 호출, 나머지는 `SKIN_SAMPLE_EMAIL` 계정의 저장된 결과를 보여줌(비용 보호)
- `PERFECT_CORP_MODE = sd` 기본(같은 사진에서 hd와 점수 거의 동일, 더 쌈)

### 4-4. 사진 → 5축 변환 (`to_axes`)
Perfect Corp 점수는 **높을수록 건강**하므로 문제 축은 뒤집습니다. 분석에는 `raw_score`, 화면 막대에는 `ui_score`(업체가 동기부여용으로 보정한 값)를 씁니다.

| 5축 | 계산 |
|---|---|
| moisture | `moisture.raw / 10` (+ 'Dry' 분류 시 −nudge) |
| oil | `(100 − oiliness.raw) / 10 × GAIN` (+ 'Oily' +nudge, 'Combination' +nudge/2) |
| sensitivity | `(100 − redness.raw) / 10 × GAIN` (+ 'Redness' +nudge) |
| pigmentation | `(100 − age_spot.raw) / 10 × GAIN` |
| trouble | `(100 − acne.raw) / 10 × GAIN` |

- `PHOTO_AXIS_GAIN = 1.0`, `PHOTO_SKIN_TYPE_NUDGE = 1.0` (업체의 Normal/Oily/Dry/Combination/Redness 분류를 축 ±1로 반영)
- 5개 항목 중 하나라도 없으면 502

## 5. 성분 유사도 · 대체품 추천 (`services/similarity.py`)

상세 평가는 `docs/similarity.md`. 요약:

### 5-1. 기본 방식 `hybrid` (적재 전 환경은 `tfidf`로 대체)

```
점수 = 0.65 × (역할 가중 TF-IDF 코사인)
     + 0.35 × (성분 기능 프로필 코사인)
     + 0.20 × (제형 일치 가산)        ← 모르면 중립
     + 판정 보정(curated): 0점 −0.15 / 2점 +0.10
```

- **IDF의 이유**: 정제수·글리세린 등 상위 6종이 제품의 51~85%에 들어 있어 단순 교집합은 무의미 → IDF가 이들을 0에 가깝게 만듦
- **역할 가중**(TF-IDF 항): 활성 1.0 · 에몰리언트 0.6 · 기타 0.35 · 계면/점증 0.25 · 용매/방부 0.2 · 오염 이름 0 · **라벨 없음 0.6**
- **기능 프로필**: 기능 9종 + 역할 3종 + 자외선 유형 2(무기/유기) = 14차원. 앞 성분일수록 크게(**15번째 성분에서 0.5**, `POSITION_HALF=15`), 확신도 1은 제외
- **제형**: 이름에서 스틱·쿠션·패드·시트·오일·폼·워터·세럼 등을 추출

## 6. 피부 궁합 · 성분 분석 (`services/skin_fit.py`) — 점수 로직의 핵심

이 모듈이 피부타입 규칙의 **정본**입니다. 결과는 `product_skin_fit`(제품 × 8타입)에 **사전 계산**되어 적재되고(`scripts/compute_skin_fit.py`), 목록 필터·정렬·홈 추천·예산 가이드·궁합 카드·전성분 칩이 모두 같은 값을 읽습니다.

### 6-1. 성분 라벨 체계 (`ingredient_functions`)
- 기능(복수) 9종: **H**보습 **B**장벽 **S**진정 **W**미백 **A**주름·탄력 **O**항산화 **P**피지·모공 **E**각질·클렌징 **U**자외선
- 역할(1개): a활성 e에몰리언트 s용매 f계면 t점증 p방부 x기타 j오염
- 플래그: **I**자극 소지 · **F**향료/알레르기 유발 · **L**건조 알코올
- 확신도 1~3. 1,686종 라벨(제품 출현 기준 94.4% 커버), 라벨 없는 ~2,600종은 궁합 근거에서 빠짐
- 내부 마커: `A`=식약처 알레르기 유발 착향제 고시 목록, `G`=일반 '향료'/'조합향료'

### 6-4. 점수식

```
성분별 기여  = 선호가중 × 위치감쇠      (활성·에몰리언트 & 확신도 ≥ 2 인 성분만)
위치감쇠     = 1 / (1 + (표기순서−1) / 15)
선호 점수    = 1 − exp( −Σ기여 / (REF[타입] × 1.9) )          # 0~1, 타입별 포화
감점         = Σ 플래그별  AVOID[타입][플래그] × min(1, BASE[플래그] + 0.25×(개수−1))
               BASE: F 0.4 · L 0.7 · I 0.5
score        = round( clip( 100 × (0.30 + 0.70 × 선호 점수) − 감점 , 0, 100 ) )
```

- `REF`(타입별 기준 규모) = 카탈로그 제품(근거 성분 3종 이상)의 선호 가중 합 **중앙값**(2026-10 실측): 옹달샘 4.1 · 물개 2.1 · 수부지 5.2 · 화산 2.3 · 사막 5.7 · 인절미 4.1 · 유리구슬 4.1 · 메밀묵 1.3
  → 중앙값 제품 ≈ 59점(무난), 중앙값 1.4배 ≈ 66점(잘 맞음)
- **근거 부족 → 판정 안 함**: 활성/에몰리언트 근거 성분이 **3종 미만이면 `unknown`** ("모르는 것을 '보통'으로 보여주지 않는다")
- 플래그 한 성분은 **가장 구체적인 하나에만** 속함(F > L > I) — 이중 감점 방지
- 기피 플래그는 **확신도 3**(또는 고시 목록 F)일 때만 인정

### 6-5. 판정 기준

| 판정 | 조건 |
|---|---|
| `good` 잘 맞음 | score ≥ **66** (그리고 아래 caution 조건에 걸리지 않음) |
| `caution` 주의 | 단일 플래그 감점 ≥ **12** 또는 감점 합 ≥ **18** 또는 score < **28** |
| `ok` 무난 | 그 외 |
| `unknown` | 근거 성분 < 3 또는 모르는 타입 |

### 6-6. 하드 제외 (목록에서 아예 뺌)
근거가 분명한 것만:
- **향료**(고시 목록 성분 또는 일반 향료) → 화산 · 유리구슬
- **건조 알코올**(확신도 3) → 수부지 · 사막 · 유리구슬
- 그 밖의 의심은 목록에서 빼지 않고 카드에서 '주의'로만 알림

### 6-7. 전성분 칩 분류 (`classify_ingredient`)
`warn`(고시 목록·일반 향료·건조 알코올, 또는 내 타입 기피 플래그) / `key`(확신도 2+ 활성·에몰리언트가 내 타입 선호 기능 보유) / `normal` / `None`(라벨 없음) — 카드의 이유와 칩 개수가 어긋나지 않도록 `evaluate`와 같은 기준.

### 6-8. 내 제품 성분 분석 (`services/product_analysis.py`)
기능 강도 `= 100 × (1 − exp(−Σ위치가중 / 2.0))` (활성 1개가 맨 앞이면 ≈ 39, 3개면 ≈ 78). **50 이상 '강함', 40 미만 '비어 있음'.** 주의 성분은 식약처 착향제 > 향료 > 건조 알코올 > 자극 순.

## 7. 추천 · 예산 가이드

### 7-1. 제품 점수 (`services/product_score.py`) — 홈과 예산 가이드가 공유

```
점수 = 0.4 × 궁합(점수/100; 판정불가·미계산은 0.5)
     + 0.3 × 별점/5
     + 0.2 × min( log10(리뷰수+1) / log10(100,000) , 1 )
     + 0.1 × 브랜드 다양성
```
- 앞 세 항은 SQL, **브랜드 다양성만 파이썬 후처리**: 이미 뽑은 목록에 같은 브랜드가 n번째로 나오면 `(1 − n×0.35)`를 곱한 값을 0.1 비중으로 반영
- 후보는 **성분 분석이 끝난 제품만**(`analyzed()` — hybrid 유사도 보유) + 단일제품 + 가격 있음 + 해당 피부타입 하드 제외 반영
- 홈은 `limit×4`개를 받아 다양성 후처리 후 자름, 24시간 캐시

### 7-2. 예산 구매 가이드 (`services/budget_guide.py`)

1. 단계별(**토너·에센스·크림·선크림**) 상위 **20개** 후보 + 예산 부족 대비 단계별 최저가 **10개** 추가. 피부타입 기피·무향·무알코올 조건, 화장대 보유품 제외
2. 단계마다 하나씩 합계 ≤ max 인 조합을 **전부** 탐색(가격 오름차순 + 가지치기; 빔서치 아님)
3. 조합 점수 = 제품 점수 **평균**
4. **1~3안**: [살 수 있는 최저 조합 합계, max]를 3구간(알뜰·균형·여유)으로 나눠 구간별 최고 점수 조합. 앞 안과 겹치는 제품 하나당 **−0.03** 감점(세 안이 같은 제품을 공유하던 문제 해결)
5. 4단계를 못 사면 **뒤쪽 단계부터** 빼며 가능한 만큼 제안(`missing_steps`, `min_possible_total` 안내)

## 8. 챗봇 · 케어 문구 · OCR · 기타

### 8-1. 챗봇 (`api/chat.py`, `services/rag.py`)
- **RAG**: 질문을 공백으로 토큰화(2글자 이상) → 제품명·브랜드·성분명 부분일치, 피부타입 하드 제외 적용, 정렬은 평점·리뷰순(로그인 사용자는 내 피부타입 궁합 점수순). 피부타입을 알면 각 제품에 `product_skin_fit`의 궁합(점수·판정·향료/알코올 여부)을 붙여 프롬프트에 "내 피부 궁합"으로 넣는다. 통용명→표준화명 매핑 7개 하드코딩(히알루론산·비타민C·센텔라·판테놀·콜라겐·레티놀 등)
- **시스템 프롬프트 요점**: 제품 사실(이름·가격·성분·평점)은 제공된 DB 데이터만 말함 / 어울리는지는 "내 피부 궁합" 판정·점수를 그대로 말하고 없으면 일반 지식임을 알림("판단 근거 부족"을 무난으로 바꾸지 않음) / 성분 자체 설명은 "일반 지식"임을 밝히고 허용 / 마크다운은 `**굵게**`만 허용 / 날씨 반영
- 기본 설정: `max_tokens` 1024, `temperature` 0.7, 타임아웃 20초/공급자, 대화 이력은 최근 것만
- 비회원은 IP당 일일 한도(`GUEST_CHAT_DAILY_LIMIT`), 초과 시 401로 로그인 유도
- **폴백**: LLM 체인 전부 실패 시 → 키워드로 질문 유형 분류(추천/대체/성분) → DB(성분 설명·기능 라벨·유사도·궁합)를 정해진 문장 틀에 채움. 환각 없음, 응답에 `mode: "fallback"` 표시

### 8-2. 오늘의 케어 문구 (`api/care_tip.py`)
- 프롬프트: 18~26자 한 문장·해요체·끝에 이모지 1개·스킨케어 팁만(우산·옷차림 금지)
- 입력: 피부타입 + 현재 날씨(체감·최저/최고·습도·구름) + 오늘 예보(강수확률·특이 날씨 이벤트)

### 8-3. 사진으로 제품 찾기 (`services/ocr.py`, `api/products.py`)
```
사진 → CLOVA OCR (필드 이어붙인 통짜 텍스트)
     → pg_trgm similarity(한글명·영문명) ≥ 0.15
     → 변형(용량·기획) 한 후보로 접기 → 상위 3개 + "찾는 제품이 없어요"
```
- **자동 선택하지 않음**: 텍스트·이미지 두 신호 모두 "카탈로그에 없는 제품"을 거절하지 못해 사용자 확인 필수
- 실사진 측정(카탈로그에 있는 제품 6개): **텍스트 top-1 6/6**, 이미지(DINOv2) 1/6. 정답 1위 점수 최저 0.290
- 호출 한도(CLOVA 무료 한도 보호): 계정당 **3회/일**, 전체 **15회/일**, 허용 이메일 면제, 카운터 장애 시 **막는 쪽**(fail-closed)
- 앞면 촬영 전제 — 뒷면은 정답 1위 0건

### 8-4. OCR 엔진 선정 과정 (`scripts/OCR_SUMMARY.md`, 36장 벤치마크)
CLOVA + region-detection이 최고: 완전 매칭 52.8%, 완전 실패 44.4%, mean CER 0.642, 장당 6.0초. 실패 원인은 화질이 아니라 블러·저대비·필기체(초해상도 FSRCNN으로 소수점까지 동일 확인). Surya(18분+ 로딩)·PaddleOCR-VL(장당 615초)·Claude Vision(키 무효)은 탈락. *이후 실서비스 방식(통짜 텍스트 + trgm)에서 실사진 22장 전부 인식 성공(장당 1.2~3.2초)으로 개선.*

### 8-5. 게이미피케이션 (`services/experience.py`, `api/personal.py`)
- 경험치: 스캔 10 · 후기 20 · 선물 20 · 주문 50 (기록에서 계산, 소급 반영)

### 8-6. 퍼스널 AI (`services/chat_tools.py`, `memory.py`, `preference.py`, `skin_report.py`, `briefing.py`, `personal_context.py`)

공통 원칙: **사실은 계산에서 오고, 모르면 모른다고 말하며, 원인을 단정하지 않는다.** 설정 `PERSONAL_AI_ENABLED`(기본 켜짐)로 한꺼번에 끌 수 있고, 도구 호출은 `CHAT_TOOLS_ENABLED`가 따로 있다.

- 도구: `find_products` · `find_alternatives` · `analyze_product` · `check_skin_fit` · `build_routine` · `recommend_for_me` · `get_skin_report` · `get_today_briefing` · `propose_add_to_cart` · `propose_add_to_closet`

**개인 컨텍스트** (`personal_context.py`): 피부타입·최근 사진 분석의 약한 항목(70점 미만)·예산·화장대(최대 12개)·마이 성분(최대 20개)을 약 1,400자(≈600토큰)로 요약해 프롬프트에 넣는다. 이메일·얼굴 사진·원본 점수는 넣지 않고, 넘치면 화장대 뒤쪽부터 뺀다. 비회원은 요약이 없다.

**AI 기억** (`memory.py`)
- 동의(`user_consents` 'ai-memory')한 사용자에게만 읽고 쓴다. 사용자가 직접 한 말만 한 줄(3~80자, 최대 20개)로 저장하고, 연락처·URL·비밀번호·프롬프트 지시문처럼 보이는 것은 거른다
- 자동 추출은 사용자 턴 3번에 한 번(단서 단어가 있거나 "기억해"라고 하면 매번), 응답 뒤 백그라운드로 돌아 실패해도 답변에 영향이 없다. LLM이 막혀도 "○○ 기억해"는 규칙으로 저장한다
- 프롬프트에는 켜져 있는(`enabled`) 최근 10개만 들어간다. 마이페이지에서 보고 고치고 끄고 지울 수 있다(API 7개)

**내 성분 취향** (`preference.py`): 후기 5점 +1.0 · 4점 +0.6 · 2점 −0.6 · 1점 −1.0, 재구매(서로 다른 주문 2번 이상) +0.8, 찜 +0.4, 화장대 +0.3을 제품별로 합쳐 [-1, 1]로 자른 뒤, 그 제품의 성분(IDF × 역할 가중, `similarity.py`와 같은 척도)에 쌓아 좋아함/피함 벡터 둘을 만든다. 제품 점수는 `코사인(좋아함) − 0.7 × 코사인(피함)`.
- **신호가 있는 서로 다른 제품이 3개 미만이거나 좋아한 제품이 없으면 켜지지 않는다**(콜드 스타트 — 적은 데이터로 취향이 있는 척하지 않음)
- 홈 추천 점수에 `BLEND = 0.2`만 섞고(후보 풀 안에서 0~1로 맞춘 값), 하드 제외된 제품은 취향이 끌어올리지 못한다. 설명은 겹치는 성분 상위 3개

**피부 변화 리포트** (`skin_report.py`): 최근 분석을 직전 분석과 항목별로 견줘 **±3점 이상**이면 좋아짐/나빠짐, 미만이면 '비슷해요'. 그 사이 화장대에 더한 제품(최대 6개) 중 그 항목을 돕는 기능 강도가 30 이상인 제품(항목당 최대 2개)을 *나란히 보여 줄 뿐* 원인으로 단정하지 않는다("날씨·수면 등 다른 요인도 있어요"). 분석이 2건 미만이면 비교하지 않는다. 눈가 구조 항목은 뺀다.

**오늘의 브리핑** (`briefing.py`): 날씨(습도 40% 이하·'건조' 예보 → 보습, 기온 5℃ 이하 → 추위, 28℃ 이상 → 더위, 습도 75% 이상 등)와 사진 분석의 약한 항목(가중 ×1.15)으로 "오늘 필요한 기능"을 정하고, **화장대에서 그 기능 강도가 30 이상이면서 가장 강한 제품**을 고른다. 문장은 전부 규칙이라 LLM이 없어도 같고, 맞는 제품이 없으면 없다고 말하며 챗봇으로 찾아 보게 안내한다. 날씨를 못 가져오면 피부 항목만으로 만든다.

## 9. 프론트엔드 로직 (`frontend/src/utils/`, `data/`)

| 파일 | 내용 |
|---|---|
| `data/skinTypeScoring.ts` | 비회원용 **클라이언트 진단**(§3과 같은 `DELTAS`·`PROFILES`·5축·유클리드 근사도). 서버 `diagnosis.py`와 값이 같아야 하며, 둘이 어긋나면 안 됨 |
| `utils/alternatives.ts` | 서버 `score`(0~1) → **백분율** 변환(`round(score×100)`, 0~100 클램프). 초록 뱃지 기준 `SIMILARITY_HIGH = 55`(hybrid 분포 기준 시드당 약 4개가 초록; 0.50→9.1개·0.55→4.0개·0.60→1.8개). **같은 제품 변형** 분리: 같은 브랜드이면서 (유사도 ≥ 99% 또는 용량·리필 표기를 뗀 이름이 같음). 절약률 = `(기준가−대체가)/기준가`, **10% 이상일 때만** "N% 저렴" 태그 |
| `utils/unitPrice.ts` | 단가 표기(1매당·10ml당·10g당·1개당). 서버가 코드만 내고 문구는 프론트 소유 |
| `utils/compare.ts` | 제품 비교: 기능 강도 차이가 `FUNCTION_GAP = 12` 이상이면 우열로 표시, 핵심 성분·주의 성분·피부 상태 비교 |
| `utils/faceCheck.ts` | 촬영 화면의 **얼굴 사전 확인(MediaPipe)**: 얼굴 폭 ≥ 0.4, 밝기 ≥ 50, 검출 신뢰도 ≥ 0.6, 두 번째 얼굴 무시 비율 0.5, 프레임 이탈 허용 5%, 촬영 가이드 얼굴 폭 0.64~0.85 |
| `utils/ingredients.ts` | 전성분 `[라벨]` 그룹 파싱, 기능명·주의 문구 표시 |

> 서버(`face_gate.py`)의 얼굴 폭 기준은 **0.60**, 프론트는 **0.4**(촬영 가이드는 0.64~0.85)입니다. 프론트가 더 느슨한 1차 확인이고 서버가 엄격한 2차 확인이라 의도된 이중 구조로 보이지만, 사용자가 프론트를 통과하고 서버에서 거절당하는 구간(폭 0.4~0.6)이 존재합니다.

## 10. 알림 규칙 (`services/notifications.py`)

- **알림을 저장하지 않고 기록에서 만들어 냅니다**(주문·포인트·후기·선물·진단에 시각이 있으므로). 저장하는 것은 마지막으로 읽은 시각(`profiles.notifications_seen_at`) 하나뿐입니다.
- 종류: 주문 접수(`order`) · 포인트 적립(`point`) · 후기 대기(`review`, 구매했지만 후기 없는 제품이 있을 때) · 선물 기록(`gift`) · **재진단 권유(`diagnosis`, 마지막 진단 후 90일 경과)**
- 한 번에 최대 30건, 최신순
- **만들지 않는 알림**: 가격 인하(가격 이력 테이블 없음), 재입고(신청 기능 없음) — 근거 없이 흉내 내지 않는다는 방침

## 11. 데이터 수집·적재 파이프라인

```
올리브영 크롤링 (crawling/*.js, Playwright)  ─┐
  카테고리 서브코드별(스킨케어·마스크팩·클렌징·선케어) │
  15개 컬럼: 카테고리·브랜드·상품명·가격·평점·리뷰수·    ├→ 정제(v5 CSV: 카테고리 교정·기획 정리·내용량 정리)
  화장품성분·내용량·이미지URL 등                      │     → scripts/load_products.py (goods_no 기준 upsert)
식약처 공공 API (data_collection/mfds_collector.py) ─┘
대한화장품협회 성분 PDF → scripts/extract_ingredient_dict.py → 성분 사전(CSV) → scripts/seed_ingredients.py
성분 해석: normalize() → 별칭 조회 → 사전 매칭 → product_ingredients
이후 배치: compute_similarities.py → similarities / compute_skin_fit.py → product_skin_fit
```

- 운영 크롤러는 **Playwright(Node)** 이고, `backend/app/data_collection/oliveyoung_crawler.py`(Selenium)와 `sample_data.py`는 초기 Task 2 시절 코드입니다. 어느 쪽이 현역인지는 코드만으로는 단정할 수 없습니다.
- 크롤링 원본(`data/raw`, `crawling/*.csv`)은 저장소에 커밋되어 있습니다. 올리브영 페이지를 수집한 데이터입니다.
